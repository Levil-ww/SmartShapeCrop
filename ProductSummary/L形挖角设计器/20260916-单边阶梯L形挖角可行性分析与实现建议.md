## 一、需求澄清：真实草图形态

### 1.1 草图还原（实测像素 → 厘米）

草图实测比例 **12.4706 px/cm**，外框 93.5 × 55 cm，右上角为**两级台阶**：

```
(cm 坐标，y 向下)
(0,0) ────────────(75,0)
  │                   │
  │                6.5│  ← 级1 深度
  │                   └────────(85,6.5)
  │                             │
  │                          3.5│  ← 级2 深度
  │                             └────────(93.5,10)
  │                                        │
  │                                     45 │  ← 右边垂直段
  │                                        │
(0,55)──────────── 93.5 ─────────────────(93.5,55)
```

### 1.2 几何本质

**8 个顶点，2 个凹角（reflex）**：

```python
# 顺时针顶点序列（cm）
[(0,0), (75,0), (75,6.5), (85,6.5), (85,10), (93.5,10), (93.5,55), (0,55)]
#         ↑凹角1              ↑凹角2
```

**尺寸链自洽校验**（两处独立吻合，证明还原正确）：

| 校验式 | 结果 |
|---|---|
| `6.5 + 3.5 = 10`，`55 − 10 = 45` | ✅ 与右边标注「45」吻合 |
| `75 + 10 + 8.5 = 93.5` | ✅ 与下边标注「93.5」吻合 |

### 1.3 与「多边 L 形」的本质区别

| 形状 | 凹角分布 | 已支持 |
|---|---|---|
| 单角 L 形 | 1 个凹角，紧贴 bbox 角 | ✅ |
| 多边 L 形（9.14–9.15） | 多个凹角，**分别贴不同的 bbox 角** | ✅ |
| **单边阶梯 L 形（本例）** | 多个凹角，**全在同一条边上、沿边错位排列** | ❌ |

> 关键差异：**多边 L 形的每个凹角各自贴一个 bbox 角；阶梯的凹角全部贴同一个 bbox 角（此处都是 tr），靠「沿边错位量」区分级别。**

用真实草图（`.venv` 环境）跑通全链路，结果出乎意料——**识别层的数据基本都对**。

### 2.2 根因定位：`corner` 四值语义无法表达「同角错位多级」

两个凹角的方向判定代码（`lshape_sketch_parser.py::_finalize_lshape_geometry`）逐一代入：

```python
# 凹角1 (950,137)，邻居 prev=(167,0) next=(-1,-91)
h_nbr=(167,0) → sx=+1 ;  v_nbr=(-1,-91) → sy=-1  →  corner = 'tr'
# 凹角2 (1118,194)，邻居 prev=(142,0) next=(-1,-57)
h_nbr=(142,0) → sx=+1 ;  v_nbr=(-1,-57) → sy=-1  →  corner = 'tr'
```

**两个凹角的 `(sx, sy)` 完全相同，因此都被判为 `tr`。**

但二者在几何上是**同一条边上的不同级别**：

| 凹角 | 方向特征 | 错位信息（丢失） |
|---|---|---|
| 凹角1 | 向右下开口 | 距上边 6.5cm、距右边 18.5cm |
| 凹角2 | 向右下开口 | 距上边 10.0cm、距右边 8.5cm |

> `corner ∈ {tl,tr,bl,br}` 只回答**「这个凹角朝向哪个 bbox 角」**，不回答**「它是该角的第几级、沿边错位多少」**。
> 这是**表达能力不足（模型缺口）**，不是算法没算出来。

### 2.3 后果：静默出错（最严重的问题）

把上述识别结果送进几何层渲染，与真实阶梯做**像素级比对**：

| 量 | 值 |
|---|---|
| 真实保留面积 | 609,888 px |
| 现有渲染面积 | 622,888 px |
| 差异 | **+13,000 px（多保留 2.1%）** |
| **IoU** | **0.9791**（1.0 = 完全一致） |

逐行最右保留像素对照：

| y_px | 真实阶梯 | 现有渲染 | 判定 |
|---|---|---|---|
| 20 | 935 | 1040 | ❌ 不符 |
| 60 | 935 | 1040 | ❌ 不符 |
| 100 | 1060 | 1165 | ❌ 不符 |
| 140+ | 1165 | 1165 | ✅ |

**可视化比对**（`scripts/diagnose/_stair_vs_current.png`）：

- **A 图**：真实阶梯 —— 右上角两级台阶
- **B 图**：现有渲染 —— **只挖了一个大矩形角，第二级台阶完全丢失**
- B 图中绿色虚线为真实轮廓参照，可见橙色填充区域**明显越过**真实边界

> ⚠️ **这是本项目最危险的失效模式（「静默失效」的又一次实例）**：
> 用户看到「识别成功」提示、G1 闸口不告警，拿到的是一个**错误的形状**，
> 且没有任何机制提示他「少了半级台阶」。9.14 多边 L 形初期也踩过同款坑。

## 三、面板决策：集成，不新开

### 3.1 结论

**集成进现有 `gui/lshape_panel.py`（「L形挖角设计」Tab），不新开面板。**

### 3.2 决策依据

| 维度 | 集成（推荐） | 新开面板 |
|---|---|---|
| **几何本质** | 阶梯是 L 形的**超集**：单角 L 形 = 1 级阶梯 | 需复制整套几何/渲染/边框链路 |
| **识别层** | **本次实测证明已能算出全部数据**，无需新算法 | 同样要复用，拆分无收益 |
| **渲染链路** | `build_lshape_mask(cuts=[...])` 已是列表入参，天生支持 N 级 | 100% 重写或伪独立 |
| **边框补全** | `apply_lshape_border_completion(cuts=[...])` 已是**列表入参** | 需重新设计 |
| **历史记录** | 复用 `TARGET_SRC_LSHAPE` 第三源，零新增 | 需第四源 + 白名单同步 |
| **用户心智** | 「挖角」是同一个概念，形状不同是参数不同 | 用户需先判断「我这是 L 形还是阶梯」 |
| **面板数量** | 保持 3 Tab | 增至 4 Tab |

### 3.3 集成的隐性收益（本项目两个「静默失效」坑）

新增几何模式必查两处硬编码，两处都**不报错**：

| 位置 | 问题 | 集成方案的收益 |
|---|---|---|
| `gui/property_panel.py:926` | `{'rect_hole':0,'rect_lshape':1,'ellipse_hole':2}` 硬编码索引 → 不同步则模板加载**静默回落 `rect_hole`** | 不新增 mode → 不受影响 ✅ |
| `core/app_settings.py:317` | `if src not in (CROPPER,POOL,LSHAPE): src=CROPPER` → 新增源则历史**静默写进圆角裁剪工具** | 不新增源 → 不受影响 ✅ |

> **「集成进现有面板、不新增 mode/历史源」的方案可同时绕过这两个坑 —— 这是集成的隐性收益，也是本报告推荐集成的技术理由之一。**

### 3.4 为什么 9.2 拆分是对的，但这次不该拆

9.2 把 L 形从水池设计器拆出独立面板，是因为**业务语义确实不同**（水池 = 素材填充 + 多洞；L 形 = 挖角形状设计），拆分后各自的心智模型更清晰。

阶梯与 L 形之间**不存在这种语义断层** —— 它们回答的是同一个问题：「这块板要挖掉哪些部分」。拆分会制造「同一件事分两个地方做」的额外认知负担。

## 四、推荐实现方案

### 4.1 核心洞察：缺的不是算法，是「形状表述」

实测证明：
- ✅ 识别层**已能检测 2 个凹角**、坐标基本准确
- ✅ OCR **已能逐角读出** 10/6.5/8.5/3.5 四个数值
- ✅ 外框尺寸**完全正确**
- ❌ 缺的是：**把这些凹角「组装成一个形状」的表述方式**

因此改造重点**不在识别层**（这是最大的好消息，原估风险的第三期可以大幅缩减）。

### 4.2 方案：`CutRect` 列表化（带「锚定角 + 沿边错位」）

现有模型的缺口在于「cut 只能贴两条外廓边」。补上「沿边错位量」即可表达任意级台阶：

```python
@dataclass
class CutRect:
    """一个待挖除的矩形。用「锚定角 + 沿边错位」表达，天然支持同角多级。"""
    anchor: Literal['tl', 'tr', 'bl', 'br']   # 锚定哪个 bbox 角（决定贴哪两条外廓边）
    offset_x_cm: float   # 沿水平方向、从锚定角起算的错位量
    offset_y_cm: float   # 沿垂直方向、从锚定角起算的错位量
    w_cm: float          # 矩形宽
    h_cm: float          # 矩形高
```

**表达能力对照**：

| 形状 | CutRect 表达 |
|---|---|
| **旧单角 L 形**（tr 挖 30×8） | `CutRect('tr', 0, 0, 30, 8)` |
| **旧多边 L 形**（tr 30×8 + bl 30×13） | `[CutRect('tr',0,0,30,8), CutRect('bl',0,0,30,13)]` |
| **本例阶梯**（两级） | `[CutRect('tr', 0, 0, 10, 6.5), CutRect('tr', 10, 6.5, 8.5, 3.5)]` |

**关键性质：旧模型是新模型的严格子集**（旧字段 `offset` 恒为 0）：

```python
# 兼容层：旧字段 → CutRect 列表，零行为变化
def cut_rects_from_legacy(l_corner, l_cut_w_cm, l_cut_h_cm, l_cuts_cm) -> list[CutRect]:
    ...  # 单角/多角均无损转换，offset 全 0
```

> **注意**：本例中「第二级」的 `offset` 恰好等于「第一级的 w/h」，但这是**本例的特例**（台阶逐级内收）；一般化设计应允许 offset 独立取值，以覆盖「台阶外扩」「间隔跳级」等变体。

### 4.3 改造清单

| 层 | 文件 | 改动 | 风险 | 说明 |
|---|---|---|---|---|
| **数据模型** | `core/geometry.py` | 新增 `CutRect` dataclass；`CropDesign` 增 `l_cut_rects` 字段（**保留 `l_cuts_cm` 作兼容入口**） | 低 | 纯新增 |
| **几何** | `core/geometry.py` | `build_lshape_mask` 的 cut 循环改遍历 `CutRect`；新增 `_rect_from_anchor_offset()` | **中** | 核心算法，需仔细 |
| **几何约束** | `core/geometry.py:308-324` | 同边约束从「尺寸和 < 边长」改为「**各级不重叠 + 不越界**」 | **中** | 规则语义重写 |
| **渲染出口** | `core/image_ops.py` | `l_shapes_px()` → `l_cut_rects_px()`；8 处 `mode=='rect_lshape'` 分支收敛 | **中高** | 见 §4.4 警示 |
| **圆角** | `core/geometry.py::build_lshape_mask` | `opposite_map` 单值查找 → 每个 CutRect 独立算内凹角方向 | 中 | |
| **识别层** | `lshape_sketch_parser.py` | **仅需给每个凹角补上 `anchor` + `offset_x/y`**（数据已在手，见 §4.5） | **低** ⬇️ | 原估高风险，实测下调 |

| **GUI** | `gui/lshape_panel.py` | 4 行「挖角 N」→ 支持**同角位子行**（父子缩进 + 「+ 追加一级」） | 中 | 交互需确认 |

**另需注意**：`core/geometry.py:308-324` 的同边约束**当前会拦住阶梯**（用 `tr+br` 拼同边阶梯实测报 `尺寸和 28cm 必须小于外边长度 24cm`）。该约束对多边 L 形（对角）成立，但对同边阶梯是**语义错误**，必须重写。

### 4.5 识别层为什么风险下调（附改造点）

实测发现识别层**已经算出了阶梯所需的全部数据**，只是打标签的方式丢了「错位」信息：

```python
# 现状：只输出 corner，丢掉错位量
all_corners.append({
    'corner': corner,            # 'tr'  ← 两个凹角都是这个
    'cut_w_px': cut_w_px,        # 靠「到 bbox 边的距离」反推 ← 阶梯下会算错
    'cut_h_px': cut_h_px,
    'concave': (int(conc[0]), int(conc[1])),   # ← 凹角真实坐标，一直都在！
    'score': float(score),
})

# 改造：直接用 concave 坐标算 anchor + offset
#   anchor   = corner（已有）
#   offset_x = |conc.x - anchor_bbox_x|   ← 从 concave 直接算，无需新算法
#   offset_y = |conc.y - anchor_bbox_y|
```

> **`concave` 坐标一直在 `all_corners` 里**，只是下游没用它来算错位量。这意味着识别层的改造是**「换个公式」而非「新算法」** —— 这是本次风险评估下调的直接依据。

**但注意**：`cut_w_px = maxx - cx` 这套公式在阶梯场景下会**算错**（本例实测：凹角1 推得 `cut_w=310px`，而真实级1 宽只有 `10cm=125px`）。改造后必须改走「相邻顶点差值」而非「到 bbox 边距离」。

## 七、结论与建议

### 7.1 直接回答

**Q1：需要打开一个面板吗？**

> **不需要，集成进现有的「L形挖角设计」面板。** 阶梯是 L 形的超集，且不新增 mode/历史源可顺带绕过两个静默失效的硬编码坑。

**Q2：应该怎么设计实现？**

> **核心是把「凹角列表」正确地翻译成形状表述**，而不是写新识别算法。引入 `CutRect(anchor, offset_x, offset_y, w, h)` 带锚定角与沿边错位的矩形模型，旧模型作为严格子集（offset 恒 0）。识别层只需用一直在手边的 `concave` 坐标补算 `offset`。

**Q3：现在的状况有多严重？**

> **比预期好，但存在一个已被触发的静默错误。** 实测本例草图：识别层 `success=True`、`g1_blocked=False`、外框与四个尺寸数值全部正确、2 个凹角都检测到了 —— 但**渲染出的形状与真实阶梯 IoU 仅 0.9791**（第二级台阶完全丢失），且**没有任何警告**。用户会拿到错误结果却以为成功。

### 7.2 三条最重要的提醒

1. **R1 静默出错优先级最高。** 它不是一个「将来可能发生」的风险 —— **用你给的这张草图实测，它现在就会发生**。当前 G1 闸口（`notches_detected != notches_consumed`）在阶梯场景下**形同虚设**（2 == 2，天然通过），因为「检测到 2 个凹角」是**对的**，错的是「把 2 个凹角组装成形状」这一步。需要一层新的「形状自洽」校验。

2. **识别层比你担心的好。** `n_detected=2`、OCR 逐角读出的 10/6.5/8.5/3.5 与草图标注**逐一对上**、`concave` 坐标一直在 `all_corners` 里可用。改造是「换公式 + 补字段」，不是「新算法」—— 这是工期从 13–20 天下调到 8–13 天的依据。

3. **边框补全仍是唯一的硬骨头**（与 9.14 多边 L 形结论一致）。台阶带来的是**非 bbox 角的凹角**，`lshape_border.py` 有 6 个函数被 `cut_corner` 字符串贯穿。

### 7.3 需要你确认的两点

1. **级数上限**：本例是 2 级。实际上限是多少？（2 级 / 3 级 / 不限）→ 决定 GUI 子行数量与交互设计
2. **是否需要变体**：除「逐级内收」外，是否还需要支持「逐级外扩」或「阶梯 + 多角混合」（如右上阶梯 + 左下挖角）？→ 决定 `CutRect` 的 `offset` 是否需独立取值（而非恒等于上级尺寸）
