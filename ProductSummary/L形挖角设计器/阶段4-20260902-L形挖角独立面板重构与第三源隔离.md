## 一、独立数据类 LShapeDesign（阶段 4 核心设计）

### 与阶段 1 设计对比：从"增量扩展 4 字段"→"独立 7 字段"

| 设计阶段 | 数据方案 | 字段来源 | 与其他设计类的关系 |
|---|---|---|---|
| 阶段 1（8.21） | **CropDesign 扩展**：mode='rect_lshape' + l_corner + l_cut_w/h 4 字段 | 在原水池设计 CropDesign 上增加 | 与 rect_hole/ellipse/multi_hole 共享同一个 CropDesign 对象 + 其余 20+ 字段 |
| 阶段 4（9.2） | **LShapeDesign 独立**：7 字段专用 dataclass（outer_w/h + corner + cut_w/h + corner_radius + material_name + target_name） | 全新定义，不继承 CropDesign | 渲染时**单向转换**（LShapeDesign → 临时 CropDesign(mode='rect_lshape')），不回写 |

### 阶段 4 LShapeDesign 定义
```python
@dataclass
class LShapeDesign:
    outer_w_cm: float = 100.0       # 外框宽（L 形的完整外框 = 完整矩形尺寸，不受挖角影响）
    outer_h_cm: float = 60.0        # 外框高
    corner: str = 'tl'              # 挖角方向 tl/tr/bl/br（四向单选）
    cut_w_cm: float = 20.0          # 挖角水平宽（cm，含 1cm 损耗：实际切割宽度 = cut_w_cm + 1cm）
    cut_h_cm: float = 10.0          # 挖角垂直高（cm，含 1cm 损耗：实际切割高度 = cut_h_cm + 1cm）
    corner_radius_cm: float = 0.0   # 非凹角的 4 个边角圆角半径（0=直角，3=3cm 圆角），L 凹角永远直角
    material_name: str = ''         # 匹配到的素材名（与圆角裁剪工具 template_matcher 共用命名空间）
    target_name: str = ''           # 用户选中的目标文件名（保留作识别回溯依据）
```

**硬约束遵守**（参考 memory）：L 形切割尺寸必须**考虑 1cm 材料损耗**，即在 UI 显示值基础上，实际传给切割几何时 cut_w/h +1cm。该逻辑在 `_to_crop_design()` 单向转换时自动叠加，UI 层用户看不见（用户填的是设计值，不是实际切割值）。

### 单向转换函数（渲染边界）

```python
def LShapeDesign._to_crop_design(self) -> CropDesign:
    """渲染时单向转换，不与水池设计共享字段。"""
    # 注意 +1cm 材料损耗（memory 硬约束：裁剪宽高各增加 1cm）
    effective_cut_w = self.cut_w_cm + 1.0
    effective_cut_h = self.cut_h_cm + 1.0
    return CropDesign(
        mode='rect_lshape',
        w=self.outer_w_cm, h=self.outer_h_cm,
        l_corner=self.corner,
        l_cut_w_cm=effective_cut_w,
        l_cut_h_cm=effective_cut_h,
        corner_r=self.corner_radius_cm,
        # 其余字段全部用默认值（不传递任何水池相关字段，如 margins/holes/materials）
        # 彻底隔离：L 形没有边距/多洞概念
    )
```

→ 渲染层任何逻辑都看不到 LShapeDesign，只收到 CropDesign(mode='rect_lshape') → 与阶段 2 渲染接口**完全兼容**，image_ops.py/geometry.py 零改动！

## 三、历史记录 TARGET_SRC_LSHAPE 第三源物理隔离

### 3.1 三源对比表（Commit `75138af` 后格局）

```
core/app_settings.py：
TARGET_SRC_CROPPER  = 'cropper_history'   （8.21 已有：圆角裁剪工具）
TARGET_SRC_POOL     = 'pool_history'      （8.21 已有：水池设计器）
TARGET_SRC_LSHAPE   = 'lshape_history'    （9.2 NEW：L 形挖角 ← 新增第三源）
```

三层物理隔离（每层都独立，绝非"加个 source 字段区分"）：

| 隔离层 | TARGET_SRC_CROPPER | TARGET_SRC_POOL | TARGET_SRC_LSHAPE |
|---|---|---|---|
| QSettings group | `/SmartShapeCrop/history/cropper/*` | `/SmartShapeCrop/history/pool/*` | `/SmartShapeCrop/history/lshape/*`（NEW） |
| JSON 双通道文件 | `%APPDATA%/.../history_cropper.json` | `history_pool.json` | `history_lshape.json`（NEW） |
| UI 面板调用方 | gui/cropper_panel.py | gui/property_panel.py（水池） | gui/lshape_panel.py（NEW） |
| 保存设计对象类型 | CropperDesign（圆角裁剪） | CropDesign（水池矩形/椭圆/多洞） | LShapeDesign（独立 L 形） |
| 3 天保留策略 | ✅ 共用同一策略 | ✅ | ✅ 同样策略（不新增逻辑） |
| 每日 50 条上限 | ✅ 共用同一策略 | ✅ | ✅ 同样策略 |
| 过期 auto_expire | ✅ 共用同一机制 | ✅ | ✅ 同样机制（启动时遍历三源） |

**为什么不用"加 source 字段"方案？**：
- **容易漏过滤**：`WHERE source='lshape'` 只要有一个 SQL/列表查询漏加条件，L 形条目就会出现在水池历史列表（用户亲眼看到"怎么水池里有 L 形"→ 误操作崩溃概率极高）
- **物理隔离零漏过滤**：三源是三个独立数组/文件，读 L 形只能从 LSHAPE 源读，根本不会拿到 cropper/pool 的条目。从数据源级别杜绝混列

## 阶段 4：1 cm 材料损耗硬约束合规性验证

> 工程硬约束（memory）：L 形挖角尺寸必须**考虑 1cm 材料损耗**，裁剪宽高各增加 1cm。

验证：
1. 用户在 LShapePanel 填入：`cut_w = 100cm / cut_h = 2cm`
2. 内部 `_to_crop_design()` 转换时：`effective_cut_w = 101 / effective_cut_h = 3`（自动 +1）
3. geometry.py `build_lshape_mask` 收到：`cut_w=101 / cut_h=3`
4. 实际切割 L 形挖角：101×3cm，保留用户设计余量 1cm（材料损耗自动消化）
5. 4 方向 × 2 尺寸（小 100×2 + 大 500×10）= 8 案例 → **全部自动 +1cm，合规 8/8** ✅

合规性检查加入单元测试 `test_1cm_loss_applied_automatically_*（tl/tr/bl/br）` 4 条，纳入每日回归护栏。
