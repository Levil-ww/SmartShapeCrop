# 2026年08月14日 水池设计器尺寸解析偏差与自洽修复

## 概述
用户在实际验证中发现草图识别结果出现**严重尺寸方向错误**与**边距回填不一致**：
- 目标文件 `吸水皮革-定制-裁剪有图-白色大理石1;60.5x133cm裁剪图` 实际为133cm×60.5cm竖版画，但程序显示 70.6×70.6cm 正方形，外框69.56×69.56，内孔11.52×5.1，边距上6/下52/左4/右42.44。
- 随后再次对比验证，外框高度被识别为70.6cm而非正确61.5cm，边距数据与识别值不一致。

经两轮迭代，共修复**4个Bug**并增强**1项强制重算策略**，最终外框133.0×60.5、内框76.0×44.5、边距6/10/14.6/42.4全部正确，109项测试通过，8/8断言覆盖自动回填与预览生成场景。

## Bug 1：PoolRenderWorker画布尺寸宽高交换逻辑矛盾（两轮反复修正）

### 第一轮表现
外框被识别为69.56×69.56cm正方形，严重偏离133×60.5。

### 第一轮修复
定位到 `PoolRenderWorker.run()`（property_panel.py）中，**在水池设计模式下错误地将 parsed.width_cm 与 height_cm 做了交换**，去除该交换后显示改善。

### 第二轮表现
外框再次显示为70.6×70.6cm，实际画布尺寸仍不对——回归测试显示"不交换"导致另一批案例出现横竖颠倒。

### 第二轮修复（最终方案）
**恢复宽高交换，但明确约束条件**：
- 文件名解析时，解析器已按"第一维度为横向词"输出（即如果文件名是 `60.5x133`，parsed.width_cm=60.5, parsed.height_cm=133）。
- 水池设计器画布逻辑采用"文件宽=竖边高度、文件高=横边宽度"的竖版场景约定，因此**必须交换一次**：
  ```python
  file_w = parsed.height_cm   # 文件名第二维 = 画布横向尺寸（竖版画时更大）
  file_h = parsed.width_cm    # 文件名第一维 = 画布纵向尺寸
  ```
- 此约定与项目记忆中硬约束"canvas尺寸需交换parsed宽高正确映射横竖方向"一致。

→ 修复后画布尺寸：**133.0 cm（横）× 60.5 cm（竖）**，与用户目标一致。

## Bug 2：QDoubleSpinBox 边距上限被夹紧（52.4cm → 50cm）

### 现象
OCR识别的right_margin=52.4cm，但GUI显示为50.0cm，边距值回填与识别值不一致。

### 根因
`gui/property_panel.py` 中四个边距QDoubleSpinBox的 `setMaximum(50.0)`，超过50cm的值被Qt自动夹到50.0。

### 修复
- 四个边距SpinBox的上限从 **50cm 提升到 200cm**：
  ```python
  self.spin_margin_top.setMaximum(200.0)
  self.spin_margin_bottom.setMaximum(200.0)
  self.spin_margin_left.setMaximum(200.0)
  self.spin_margin_right.setMaximum(200.0)
  ```
- 200cm 足以覆盖极端大边距场景（如外框200cm、内框20cm、单边90cm）。
- 与项目记忆中"Margin输入字段上限必须提升到200cm以容纳OCR超过50cm结果"的硬约束一致。

## Bug 3：_need_recalc_from_target 强制重算触发逻辑混乱

### 现象
OCR已识别出正确的边距，但强制重算逻辑无差别触发，将正确值用纯几何比例覆盖，引入额外误差。

### 根因（sketch_parser.py L1415-1481）
1. `_need_recalc` 初始化默认True，即便没有任何偏差条件也会强制重算。
2. 触发条件缺少合理偏差阈值，OCR值与目标值差1%也会重算。

### 修复
1. **初始化为 False**：默认不重算，仅当条件命中才切换为True。
2. **>20%偏差才触发**：
   ```python
   ocr_area = ocr_outer_w * ocr_outer_h
   target_area = filename_outer_w * filename_outer_h
   area_deviation = abs(ocr_area - target_area) / target_area

   ocr_geom_self_consistent = (abs(ocr_outer_w - ocr_inner_w - ocr_left - ocr_right) < 2.0 and
                               abs(ocr_outer_h - ocr_inner_h - ocr_top - ocr_bottom) < 2.0)

   if area_deviation > 0.20:
       if not ocr_geom_self_consistent:
           # 偏差>20% 且 OCR自洽性差 → 按像素比例强制重算全部值
           _need_recalc = True
       else:
           # 偏差>20% 但 OCR 几何自洽 → 仅覆盖外框尺寸为文件名目标值
           # 内框 + 边距保留 OCR 值，交给方向矫正（Case1/2）处理
           _need_recalc = False
   ```
3. **保留OCR自洽值的策略兜底**：若OCR内部边距和内框满足几何关系，不重算，保留可信度高的边距。

## Bug 4：OCR双向自洽检测Case 2 过度交换（边距被连带交换，语义丢失）

### OCR双向自洽检测背景
OCR可能把外框尺寸（width×height）识别成反方向，需做两种验证：
- **Case 1**：默认方向 OCR自洽？→ top+bottom+inner_h = outer_h, left+right+inner_w = outer_w。
- **Case 2**：反向 outer↔inner 自洽？→ 某些标注习惯把"内框尺寸"写在更显眼的位置，被误识别为外框。

### 原逻辑缺陷
Case 2命中时，不仅交换了 outer_w↔inner_w 和 outer_h↔inner_h，还**连带交换了 top↔left 和 bottom↔right**，导致边距语义混乱（top值变成了left的识别值）。

### 修复
```python
# Case 2：仅交换 outer 和 inner 尺寸，边距保持原语义
if case2_self_consistent and not case1_self_consistent:
    # 正确做法：outer 与 inner 互换
    final_outer_w, final_inner_w = ocr_inner_w, ocr_outer_w
    final_outer_h, final_inner_h = ocr_inner_h, ocr_outer_h
    # 边距保持 top/bottom/left/right 语义不变
    final_top    = ocr_top
    final_bottom = ocr_bottom
    final_left   = ocr_left
    final_right  = ocr_right
```
→ 边距语义（top=上，left=左）永远稳定，只有尺寸维度可能被修正。

## 经验教训
1. **画布尺寸的横竖映射要写进代码注释并配单测**：PoolRenderWorker的"文件名解析宽⇄画布竖高、文件名解析高⇄画布横宽"约定容易在修复Bug时被误删，必须在源码旁写明注释，并增加针对竖版画的单元测试。
2. **SpinBox上限不是验证，是显示UI约束**：应设置得远大于业务预期最大值（×2~×4），真正的边界校验留在业务逻辑层。用50cm作上限等价于在UI层悄悄改写用户数据，调试极难定位。
3. **强制重算"默认关 + 条件开"更安全**：偏差阈值与OCR自洽性双重判定后才触发重算，能避免把准确的OCR结果覆盖为粗糙的像素比例值。
4. **Case 2（outer↔inner反向）语义边界必须明确**：反向场景只交换尺寸维度，不交换边距方位；一旦边距方位混淆，后续所有显示与导出都会呈现"上≠上、左≠左"的隐蔽错误。
