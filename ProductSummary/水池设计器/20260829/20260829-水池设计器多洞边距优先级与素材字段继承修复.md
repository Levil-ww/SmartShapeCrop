# 2026年08月29日 水池设计器 多洞边距三级优先级兜底 与 洞数据重建材质字段继承修复

## 概述
T5（逐洞独立边距+GUI逐洞显示）合入后，下午用户拿真实多洞素材（花型"安妮森林"）跑一轮完整出图流程，暴露两个阻断性问题：
1. **洞1左边距误识为3.6cm，实为36cm**——数量级错误（小数点位置），根因是边距校验阶段的全局margin被轴向cap拒绝后，**fallback直接取逐洞最小值3.6而非保留真实全局值36**；
2. **内挖填充为米色背景而非匹配的"安妮森林"花纹**——根因是多洞模式下`HoleInfo`数据从设计层重建（GUI切换/撤销/重做）时只复制尺寸字段，丢失了`pool_inner_material_image`（内挖素材图）等材质类字段，导致渲染看到的是缺省米色。

共2条子问题（各含一条根因+一条修复）。修复：①**三级优先级兜底（全局有效值→逐洞分配→最小值）**；②**洞数据重建全字段深拷贝继承**。全量回归：268 passed，0 regress。

## 问题一：洞1左边距 36 误识为 3.6（15:25）

### 现象
- 输入草图：外框98×433，洞1 45×37.5，真实左边距=36cm（草图靠近左边缘显式标注36）
- 程序输出：洞1左=3.6cm，导致洞1左侧与外框几乎贴边，花纹被裁掉约32cm宽

### 根因链（逐步溯源）
| 步骤 | 变量/函数 | 取值 | 说明 |
|---|---|---|---|
| 1 | OCR原始识别 | 候选={36.0(conf=82), 3.6(conf=76)} | 两种token都存在（同一标注位置有时被拆成"3""6"和"."） |
| 2 | 全局 margin_left 轴向cap校验 | 98×0.9=88.2；36.0≤88.2→**通过** ✅ | 全局字段实际合法，不该被拒 |
| 3 | 解析→渲染桥接代码（property_panel_workers.py T5版） | if `global_margins.left > outer_w×0.9 or global_margins.left < 0.2`:  **取逐洞最小值兜底** | 🔴 关键BUG：**反向判断**。代码误把条件写成了`global_margins.left >= 0.2 and not (_check_ok)` → 即使check_ok仍走到fallback分支（一个off-by-one取反错误） |
| 4 | fallback到`min(hole.margin_left for all holes)` | = 3.6cm | 洞2左5.2 + 洞1左3.6 → min=3.6，被当作最终左边距 ❌ |

### 根因小结
不是OCR的错，也不是cap的错，是**兜底优先级写反**：合法的全局有效值被错误拒绝后，直接跳入了"逐洞最小值"这种极保守的兜底。

## 问题二：修复——三级边距兜底优先级（15:25）

### 三级优先级策略（从高到低）
```
Level 1 全局有效值（Highest）
    └─ if 轴向cap通过 → 直接使用全局边距，作为各洞共享起点
Level 2 逐洞区域分配值
    └─ 若该洞自身在解析阶段绑定到独立边距值，且该值也通过轴向校验（hole.w≈outer_w-ml-mr），则覆盖全局
Level 3 保守最小值兜底（Lowest）
    └─ Level 1+2 均无，才取所有洞同字段的最小有效值
```

### 修复代码（property_panel_workers.py，原逻辑完整重写）
```python
def _resolve_hole_margins(hole, hole_index, global_margins, outer_w_cm, outer_h_cm, all_holes):
    """
    三级优先级边距解析
    返回该洞的 (mt, mb, ml, mr)
    """
    def resolve(field_name, hole_val, global_val, axis_cap, sibling_vals):
        # Level 1：全局有效值（先尝试用整体草图的值）
        if global_val is not None:
            if 0.2 <= global_val <= axis_cap:
                return global_val
        # Level 2：逐洞自身绑定值（若识别到独立值且合理）
        if hole_val is not None:
            if 0.2 <= hole_val <= axis_cap:
                return hole_val
        # Level 3：所有兄弟字段的最小有效值兜底
        candidates = [v for v in sibling_vals if v is not None and 0.2 <= v <= axis_cap]
        if candidates:
            return min(candidates)
        # 最后防线：若全空，返回全局默认或 5.0
        return global_val if global_val is not None else 5.0

    mts = [h.margin_top_cm for h in all_holes]
    mbs = [h.margin_bottom_cm for h in all_holes]
    mls = [h.margin_left_cm for h in all_holes]
    mrs = [h.margin_right_cm for h in all_holes]

    return (
        resolve('mt', hole.margin_top_cm,    global_margins.top,    outer_h_cm * 0.9, mts),
        resolve('mb', hole.margin_bottom_cm, global_margins.bottom, outer_h_cm * 0.9, mbs),
        resolve('ml', hole.margin_left_cm,   global_margins.left,   outer_w_cm * 0.9, mls),
        resolve('mr', hole.margin_right_cm,  global_margins.right,  outer_w_cm * 0.9, mrs),
    )
```

### 对问题一的重算结果（修复后）
```
Level 1：global_margins.left = 36.0 ，0.2 ≤ 36.0 ≤ 98*0.9=88.2 → 通过 ✅
→ 直接返回 36.0，不再进入 Level 3
洞1左最终=36.0cm 正确 ✅
```

## 问题三：内挖填充为米色背景而非「安妮森林」花纹（15:25）

### 现象
- 用户在GUI中选好花纹"安妮森林"→ 切换到多洞模式 → 点生成设计
- 期望：内挖矩形内填充"安妮森林"图案
- 实际：内挖矩形内填充统一米色（PoolDesign默认背景色 `#F2E6C9`）

### 根因：洞数据重建丢失材质字段
`gui/property_panel_layers.py` 中，每当用户：切换单洞⇄多洞模式、撤销/重做、导入草图触发刷新，会调用**`_rebuild_holes_from_design`**函数重新构造holes[]。
该函数T4-T5版本仅复制**尺寸类**字段：
```python
# T4-T5错误实现
def _rebuild_holes_from_design(design):
    new_holes = []
    for old in design.holes or []:
        new = HoleInfo(
            hole_index=old.hole_index,
            x_cm=old.x_cm, y_cm=old.y_cm,
            w_cm=old.w_cm, h_cm=old.h_cm,
            corner_radius_cm=old.corner_radius_cm,
            # 🔴 只复制了尺寸类字段！下面这些材质/非尺寸字段全部没复制
            # pool_inner_material_image → None
            # material_id → None
            # pool_hole_transparent → 默认值
            # ... 等十余字段全部丢失
        )
        new_holes.append(new)
    return new_holes
```
→ 每次重建后，`new_hole[i].pool_inner_material_image is None`，渲染器拿到None就填米色。

## 问题四：修复——全字段深拷贝继承（15:25）

### 方案一（最初版）：逐字段手补
手动把漏掉的9个材质字段一个个加进构造器。**被否决**：后续再加字段仍会忘记复制，相同bug会反复出现。

### 方案二（最终版）：基于 dataclasses.replace + 深拷贝
```python
import copy
from dataclasses import replace

def _rebuild_holes_from_design(design):
    """
    多洞模式下洞数据重建：默认深拷贝原HoleInfo全部字段，
    仅覆写那些明确需要重建的（如x/y坐标由几何重算）。
    新增任何HoleInfo字段都无需修改本函数——自动继承。
    """
    new_holes = []
    for old_hole in design.holes or []:
        # 1. 以old_hole为底板生成新实例，自动继承所有字段
        new_hole = replace(old_hole)

        # 2. 关键引用类型字段（素材图数组等）必须深拷贝，避免新老hole共享底层数组
        for field_name in ('pool_inner_material_image',
                           'pool_inner_material_mask',
                           'decoration_layers'):
            val = getattr(new_hole, field_name, None)
            if val is not None:
                setattr(new_hole, field_name, copy.deepcopy(val))

        # 3. 仅对需要"重建"的字段做显式覆盖（几何重算x/y）
        new_hole.x_cm, new_hole.y_cm = _calc_hole_position_from_margins(
            new_hole, design.canvas_w_cm, design.canvas_h_cm
        )
        new_holes.append(new_hole)
    return new_holes
```

### 优势
| 维度 | 手补9字段（弃用） | dataclasses.replace + 深拷贝（采用） |
|---|---|---|
| 遗漏风险 | 高（下次加字段又忘） | 零风险（自动继承） |
| 改动量 | 每次+字段必改本函数 | 改本函数0次，除非新增引用类字段才需进深拷贝白名单 |
| 回归面 | 9个字段需逐一验证 | 仅2个引用类字段（素材图/mask）+装饰层需测深拷贝一致性 |

## 关键决策沉淀
1. **兜底永远放在最后一位**：全局值 > 逐洞绑定值 > 所有洞最小值。任何短路跳级都可能产生"合法值被保守值覆盖"的数量级错误（36→3.6）。
2. **数据重建函数永远"默认继承、覆写少量"，而非"默认空白、手动补字段"**。HoleInfo 20+字段手补9个必漏，`dataclasses.replace` 零心智负担 + 自动化未来扩展。
3. **引用型字段深拷贝白名单**：素材图、mask、图层列表这类"共享底层numpy数组/列表"的字段，不做深拷贝会造成修改一个洞影响其他洞（或原设计）。维护一个小的白名单比维护全量字段清单的心智成本低得多。
4. **全量回归当门禁**：本次268项全通过是最终置信度来源。每次修复无论多小，都必须跑全量pytest，防止"修了这个洞、漏了那个洞"。
