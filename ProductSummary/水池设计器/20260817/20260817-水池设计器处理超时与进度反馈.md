# 2026年08月17日 水池设计器 处理超时与进度反馈

## 概述
用户反馈水池设计器长时间处于"处理中"状态且控制台无任何日志输出，体验极差。经诊断，根源在于OCR调用冗余（无早退出机制）、T0枚举无限循环（无超时保护）、缺乏UI进度反馈、日志级别过高导致INFO级日志被过滤。本篇涵盖16:35的完整修复方案。

---

## 问题诊断

### 现象
1. 点击识别后按钮变灰，状态显示"处理中..."，持续1-2分钟无任何反馈
2. 控制台无日志输出，无法判断是卡死还是在正常运行
3. UI进度条永远停在0%或不显示

### 根因分析（四重叠加）

| # | 根因 | 影响 |
|---|---|---|
| 1 | OCR高置信度结果未及时退出 | 即使第一个ROI已识别到高置信度数字，仍继续跑完所有ROI×所有预处理×所有PSM组合 |
| 2 | T0枚举无超时保护 | `T0_MAX_ITERATIONS`设置过大（100万+），极端情况下穷举4万种组合可能超时 |
| 3 | 无进度回调机制 | 解析函数内部不向UI汇报进度，进度条是装饰性的假进度 |
| 4 | 日志级别过高 | `log_setup.py`默认级别为WARNING，INFO及以下被过滤，即使正常运行也无输出 |

---

## 修复方案

### 修复一：OCR高置信度早退出（sketch_parser.py）

在`_ocr_targeted_region`和`_robust_ocr_subimage`中增加早退出逻辑：
- 单个ROI识别到置信度≥95%且数字≥2位时，立即终止该ROI的其余预处理/PSM组合
- 返回当前最优结果，不再穷举

### 修复二：T0枚举超时保护（sketch_parser.py + config.py）

| 修改点 | 说明 |
|---|---|
| config.py | `T0_MAX_ITERATIONS` 从100万降至10万 |
| sketch_parser.py | T0枚举循环内增加**10秒硬超时** + 每1000次迭代检查一次 |
| sketch_parser.py | 超时时返回当前最优解而非崩溃，保证"有结果输出" |

```python
# 伪代码示意
start_time = time.time()
for idx, combo in enumerate(all_combinations):
    if idx % 1000 == 0 and time.time() - start_time > 10.0:
        logger.warning("T0 enumeration timeout at 10s, returning best-so-far")
        break
    # ... 评估当前组合 ...
```

### 修复三：UI进度回调（sketch_parser.py + property_panel.py）

| 模块 | 修改内容 |
|---|---|
| sketch_parser.py | `parse_sketch()`增加`progress_callback: Callable[[int, str], None]`参数，各阶段汇报进度（0-100% + 文字说明） |
| property_panel.py | 调用时传入进度回调，更新UI进度条和状态文字 |

进度阶段划分（共约12个节点）：
- 10%: 图像加载与预处理完成
- 25%: L1方向标签检测完成
- 40%: 几何检测完成（外框/内框定位）
- 60%: L2针对性ROI OCR完成
- 80%: L3全图OCR兜底完成
- 90%: T0枚举数值分配完成
- 100%: 最终几何校验完成

### 修复四：日志级别调整（log_setup.py）

将默认日志级别从`WARNING`改为`INFO`，确保：
- OCR调用记录可见
- 各阶段完成标记可见
- 超时/早退出等关键决策可见

| 最坏情况（超时保护） | 可能卡死>5分钟 | 10秒强制返回最优解 |

## 经验教训
1. **任何穷举/枚举必须设上限**：无超时保护的穷举是定时炸弹，迟早会遇到极端输入
2. **早退出机制不可省略**：OCR、搜索等场景，得到"足够好"的结果就应停止，不要追求"绝对最优"
3. **进度反馈影响用户感知**：同样耗时30秒，有进度条用户觉得"程序在努力"，无进度条用户觉得"程序卡死了"
4. **日志级别默认不宜过高**：生产环境默认INFO级，出问题时才有迹可循；WARNING+会丢失太多关键信息
5. **超时应返回降级结果而非抛异常**：用户宁可接受次优结果也不愿意程序卡死或崩溃
