# 2026年08月17日 水池设计器 架构风险评估与线程安全

## 概述
用户提供了一张描述程序中高级与中级风险的示意图，要求验证图中描述的8个风险点是否存在、评估风险严重程度、评估图中建议的可行性并提出修复方案。同时在分析过程中发现了额外的线程安全问题。本篇在16:00完成全面的风险评估报告。

---

## 风险验证与分析结果

### 风险一：黄金参数硬编码（高级风险 ⚠️）

| 验证项 | 结果 |
|---|---|
| 是否存在 | ✅ 已确认 |
| 位置 | `core/config.py` 硬编码 + `sketch_parser.py` 大量引用 |
| 严重程度 | 高级 |
| 图中建议可行性 | 可行 |

**问题描述**：黄金规格（外框133×60.5、内孔76×44.5、边距6/10/14.6/42.4）分散在config.py硬编码和sketch_parser.py多个函数中，修改一处需同步多处，极易出现不一致。

**修复建议**：
- 集中到`PoolDesignerGoldenConfig`单一数据类
- sketch_parser.py通过引用该类获取值，不再分散硬编码

---

### 风险二：方向矫正规则多重判定（中级风险 ⚠️）

| 验证项 | 结果 |
|---|---|
| 是否存在 | ✅ 已确认 |
| 位置 | sketch_parser.py中3处方向矫正逻辑 + property_panel.py中2处 |
| 严重程度 | 中级 |
| 图中建议可行性 | 可行 |

**问题描述**：方向矫正（横版↔竖版）存在多重判定和保护分支：OCR自洽时不矫正、偏差>33%才矫正、矫正需同时交换outer/inner/margin。5处逻辑分散，容易出现"A处矫了B处没矫"的不一致。

**修复建议**：
- 抽取单一`_correct_orientation(result, target_aspect)`函数，所有方向矫正决策集中此处
- 统一输出：矫正后8字段 + 是否矫了flag，避免各模块自行判断

---

### 风险三：复杂度评估策略过于粗暴（中级风险 ⚠️）

| 验证项 | 结果 |
|---|---|
| 是否存在 | ✅ 已确认 |
| 位置 | sketch_parser.py L1复杂度评估阈值 |
| 严重程度 | 中级 |
| 图中建议可行性 | 需细化 |

**问题描述**：L1复杂度评估4项指标（边缘密度>15%/连通组件>200/最大矩形<10%/长宽比>5:1）任一触发直接放弃识别。真实草图中某张图纸可能只是字迹多但标注清晰，被粗暴拒绝后用户只能手动输入。

**修复建议**：
- 由"硬判断"改为"风险评分"：0-100分，>80才跳过
- 中等风险（40-80分）：给出警告但仍尝试L2+L3识别，最终结果sc<0.7时提示用户复核
- 阈值配置化：阈值移到config.py，便于现场调优

---

### 风险四：OCR依赖Tesseract且大量补丁逻辑（高级风险 ⚠️）

| 验证项 | 结果 |
|---|---|
| 是否存在 | ✅ 已确认 |
| 位置 | sketch_parser.py OCR相关10+函数 |
| 严重程度 | 高级 |
| 图中建议可行性 | 部分可行 |

**问题描述**：OCR依赖Tesseract且存在大量补丁逻辑（3×缩放、6种PSM、3种预处理、黄金对加权、多位数合并、相邻token拼接等），形成"补丁堆补丁"的技术债。任一Tesseract版本升级都可能连锁破坏。

**修复建议**：
- 短期：抽象`SketchOcrEngine`接口层，当前实现为`TesseractSketchOcr`，封装所有预处理+PSM+多位数合并细节
- 中期：预留PaddleOCR/商业云OCR等替代实现接口
- 长期：OCR前级识别精度问题需独立评估，不应在数值分配层继续打补丁

---

### 风险五：sketch_parser.py单文件过大（中级风险 ⚠️）

| 验证项 | 结果 |
|---|---|
| 是否存在 | ✅ 已确认（约2500+行） |
| 位置 | `core/pool_designer/sketch_parser.py` |
| 严重程度 | 中级 |
| 图中建议可行性 | 可行 |

**问题描述**：单文件包含：L1复杂度评估、L2几何检测、L3 OCR识别（含多个子函数）、数值候选生成（3条路径）、T0枚举分配、方向矫正、几何校验等多个模块。内聚度过高，修改一处易触发其他模块回归。

**修复建议**：拆分4模块：
```
pool_designer/
├── sketch_complexity.py   # L1复杂度评估
├── sketch_geometry.py     # L2几何检测（外框/内框定位）
├── sketch_ocr.py          # L3 OCR（封装Tesseract调用+多位数合并）
└── sketch_assigner.py     # 候选生成+T0枚举+方向矫正+几何校验
```

### 风险六：水池模式尺寸交换规则多处重复（中级风险 ⚠️）

| 验证项 | 结果 |
|---|---|
| 是否存在 | ✅ 已确认 |
| 位置 | sketch_parser.py（2处） + property_panel.py（3处） |
| 严重程度 | 中级 |
| 图中建议可行性 | 可行 |

**问题描述**：水池设计模式下，因草图方向与设计画布方向不同，外框宽高需swap（file_w=parsed.height_cm, file_h=parsed.width_cm）。此规则在5处重复实现，新增功能时极易忘记swap导致尺寸颠倒。

**修复建议**：
- 在sketch_parser.py的返回结果中新增`is_pool_mode`字段
- sketch_parser.py内部统一完成swap后再返回，调用方（property_panel.py）不再关心方向交换细节
- 调用方直接使用`.outer_w_cm / .outer_h_cm`即可，保证一源真值

---

### 风险七：草图解析缓存仅进程内且线程不安全（高级风险 ⚠️）

| 验证项 | 结果 |
|---|---|
| 是否存在 | ✅ 已确认 |
| 位置 | sketch_parser.py 全局缓存变量 + `_SketchParseWorker`多线程访问 |
| 严重程度 | 高级 |
| 图中建议可行性 | 可行 |

**问题描述**：草图解析结果（geometry_cache、ocr_cache）使用全局dict缓存。当多个`_SketchParseWorker`线程并发运行时（用户连续上传、或快速切换面板），dict读写无锁保护，可能出现：
- 读取到半写入的脏数据（keys不完全）
- 两个线程同时写同一key导致值覆盖
- 极端情况下Python dict内部结构损坏

**修复建议**：
- 短期：使用`threading.RLock`包裹所有cache读写，保证并发安全
- 中期：使用`functools.lru_cache`装饰纯函数，替代手动dict管理
- 长期：缓存持久化（磁盘），进程重启不丢失，同时天然隔离线程冲突

### 风险八：错误信息为技术描述对用户不友好（中级风险 ⚠️）

| 验证项 | 结果 |
|---|---|
| 是否存在 | ✅ 已确认 |
| 位置 | property_panel.py 中各错误提示MessageBox |
| 严重程度 | 中级 |
| 图中建议可行性 | 可行 |

**问题描述**：错误提示直接展示技术细节，如：
- "'set' object does not support item assignment"
- "T0 enumeration timeout at 10s"
- "OCR engine not found, pytesseract import failed"

用户无法理解，也无法据此采取行动。

**修复建议**：
- 建立错误码映射表：技术异常 → 用户友好文案 + 建议操作
  ```
  TECH_ERROR_SET_ITEM → "草图解析临时异常，请点击『重新识别』按钮重试"
  TECH_ERROR_TIMEOUT  → "识别耗时过长，已返回当前最优结果。如数值不准，请手动调整或使用更清晰的草图"
  TECH_ERROR_NO_OCR   → "未检测到OCR组件，当前使用几何估算模式。如需高精度识别，请联系技术支持安装Tesseract"
  ```
- 错误MessageBox同时保留"查看详情"折叠区，技术细节放里面，便于用户截图反馈时携带调试信息

## 额外发现：线程安全问题（高级风险 ⚠️）

在风险七排查过程中，额外发现`property_panel.py`中`_pool_spin_values`（8个QDoubleSpinBox值的缓存dict）同样存在线程安全问题：
- `_on_sketch_parsed`回调（后台线程发出，但在主线程执行，安全）
- `_pool_recalc_inner_from_margin`（用户点击SpinBox触发，主线程，安全）
- **`_SketchParseWorker.run`中直接读取spin值**（不安全！后台线程读Qt GUI对象）

**修复建议**：后台线程启动前，先在主线程快照8个spin值，传给worker。worker只读本地快照，不跨线程访问Qt对象。

| 优先级 | 风险项 | 预估工时 | 原因 |
|---|---|---|---|
| P0 | 风险七：缓存线程安全 + 额外发现 | 4h | 直接影响数据正确性，高并发下必现 |

| P1 | 风险六：尺寸交换规则统一 | 3h | 多处分发必出不一致，影响水池模式核心流程 |

## 经验教训
1. **风险评估要动手验证**：用户提的风险点不能凭印象回答"应该有/没有"，必须进代码读、搜、查引用，才能准确定位严重程度和修复范围
2. **线程安全是水池模式隐患**：引入QThread后台解析后，所有跨线程访问的共享数据（缓存dict、GUI对象）都必须逐个审查
3. **技术债积累有临界点**：OCR补丁堆补丁、5处重复swap等，短期看"能跑就行"，但会在后续每次修改时×2放大工作量
4. **错误信息也要做产品设计**：错误提示是用户体验的一部分，"抛异常给用户看"是开发偷懒，应映射为用户能理解、能采取行动的文案
