## 问题一：PhaseA 消包络盒与 PhaseB OCR 投票 两次独立遍历

### 现象
原流程 PhaseA（去重消包络盒）对 `hole_candidates` 列表做一次 for 循环，标记每个候选的 enclosing_box；PhaseB（OCR 加权众数）又对同一列表做一次 for 循环，计算每个候选的 margin_ocr_value。两次循环逻辑独立但遍历对象相同，总循环次数 2×N（N 为洞候选数，通常 3-15）。

### 根因
8.29 分阶段开发时 PhaseA/B 为独立 PR 合并，未做后序流程融合。

### 修复
**单次遍历合并 PhaseA+B**：将两个阶段的计算逻辑合并到一次列表推导中。

| 阶段 | 旧代码 | 新代码 |
|---|---|---|
| 洞候选迭代 | PhaseA: `for h in hole_candidates:` + PhaseB: `for h in hole_candidates:` | `[(enclosing_box(h), weighted_mode(h.ocr_values)) for h in hole_candidates]` |
| 计算顺序 | 先全部算 enclosing_box，再全部算 weighted_mode | 每个候选同时算两项，顺序不影响结果（两函数无状态共享） |

**行数**：PhaseA 32 行 + PhaseB 41 行 → 合并 17 行（-79%）

## 问题二：洞优先级 3 次 sort 重复执行

### 现象
`_prioritize_holes()` 函数原执行 3 次 sort：
1. 按 `(x, y)` 坐标排序（左上优先）
2. 按 `area` 降序排序（大洞优先，取 top-5）
3. 再次按 `(x, y)` 坐标排序（恢复显示顺序）

三次 sort 各 2-4 行，且 sort 对象为同一 list，共 11 行。

### 根因
8.29 逐洞功能分 PR 合并时未统一排序 key。

### 修复
合并为 **1 次 tuple key 排序 + 1 次切片**：
```python
# 原：3 次 sort（11行）
cand.sort(key=lambda c: (c.x, c.y))        # 第1次
cand.sort(key=lambda c: -c.area)           # 第2次
top5 = cand[:5]
top5.sort(key=lambda c: (c.x, c.y))        # 第3次

# 新：1 次排序 + 切片（3行）
cand.sort(key=lambda c: (-c.area, c.x, c.y))  # area降序 为主，x/y升序 为次
top5 = cand[:5]
```
tuple key 规则：`(-area, x, y)` — area 大者排前（等价 area 降序），面积相同时按左上坐标排序。取前 5 个后，剩余顺序已为 (x,y) 升序，无需二次 sort。

**行数**：11 行 → 3 行（-73%）

## 问题三：逐洞边距计算重复调用 detect_rect

### 现象
`_compute_effective_margins_per_hole()` 对每洞调用 `detect_rect(hole_crop_img)` 重新做矩形检测。但洞裁剪图 `hole_crop_img` 是 PhaseA 时已从整图裁切出的小图（通常 200×200px 内），detect_rect 返回的矩形四角坐标其实就是图的 (0,0,W,H)——因为 PhaseA 裁切时已严格对齐洞边界。

### 根因
PhaseA 裁切后直接丢弃了边界信息，逐洞函数无从知道已经对齐，安全起见重新执行了一次 detect_rect（冗余）。

### 修复
PhaseA 裁切时把 `(w, h)` 附加到候选对象：`candidate.cropped_size = (w, h)`；`_compute_effective_margins_per_hole()` 检测到该字段存在则直接用，跳过 detect_rect 调用。
- 结果：detect_rect 调用次数从 `3-15 次/草图` → `0 次/草图`
- 性能：10 洞草图 Phase 边距阶段从约 450ms → 约 30ms（**15× 提升**，主要是 cv2 开销减少）

## 经验教训
1. **分 PR 合并后必须做一次流程融合**：8.29 PhaseA-E 分阶段开发完成 + 独立 PR 合并通过，但未做流程级联优化，留下了双遍历/三排序等明显冗余。阶段型功能完成后，应安排一次"整理提交"专门做融合与去重
2. **输出哈希验证是代码精简的黄金护栏**：先写好 N 张典型输入的输出快照，再做精简，最后逐一比对快照——100% 匹配则精简安全，不必逐条读代码逻辑
3. **"裁切后重检测"是常见冗余模式**：图像裁切后若裁切逻辑已保证边界对齐，裁切尺寸应作为元数据附带，下游函数直接读取，不再重复检测。该模式在图像处理代码中重复出现率高，值得批量扫描治理
