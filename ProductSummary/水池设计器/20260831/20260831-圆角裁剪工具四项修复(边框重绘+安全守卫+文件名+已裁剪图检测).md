## 问题一：圆角裁剪边框重绘问题（`055ea9b`）

### 现象
用户案例：塞纳时光 34.3×207.9cm 圆角 3.3cm，裁剪后边框圆弧宽度出现 **2-3px 不均匀**（上弧 10px / 左弧 12px / 下弧 8px），肉眼可见左侧圆弧比右侧略粗。

### 根因
`core/image_cropper_mask.py::_build_corner_clip_mask` 构建 sentinel 层 mask 时的操作顺序错误：
1. 先执行 `cv2.bitwise_and(clip_mask, border_mask)`（裁剪掉边框层外像素）
2. 再执行 sentinel 层写入

由于 clip 先做，sentinel 层在 clip 裁剪边界处被多切掉一圈（约 1-2px），传给 `sector_render.py::_redraw_border_on_corner` 时拿到的 sentinel 区**边界不完整**，导致 `_redraw_border_on_corner` 从 sentinel 取色时部分颜色参考点丢失，最终边框宽度在个别方向略窄/略宽。

### 修复（双文件）

| 文件 | 修复项 | 说明 |
|---|---|---|
| `image_cropper_mask.py` | 操作顺序反转 | 先 `sentinel_layer.fill()` 写入 sentinel 层像素，再 `bitwise_and(clip_mask)` 做裁剪。sentinel 与 clip 的先后顺序严格为：先画后裁。裁剪后 sentinel 仍保留 clip 边界内的完整像素 |
| `sector_render.py` L309 | 边界检查放宽 1px | `is_in_border_region` 的距离判定从 `>= 1` 改为 `>= 0`。抗锯齿情形下距离计算会有 0.5px 浮点近似，放宽 1px 避免合法 sentinel 像素被误判为"越界" |

### 验证
7 张对照图（test_border_before.png → test_border_after.png）：边框宽度 min/max 方差从 3.1px → 0.4px，全方向 10px ± 0.5px 内通过。✅（对照图已于 9.2 归档至 `_archive/debug_output_20260902/`）

## 问题二：圆角裁剪安全性约束（`8c250e0`）

### 现象
fuzz 测试（随机参数 1000 组）发现 3 组崩溃案例：`cv2.error: ... borderType=...`，堆栈定位到 `cv2.copyMakeBorder` 传入 `negative thickness`。人工回溯为间隙层分类失败时，`_compute_border_thickness` 返回 -2（厚度估算公式在间隙宽度=0 时计算结果为负）。

### 修复（core/image_cropper_border.py）
新增**两处硬守卫**：

```
守卫1（立即生效）：thickness = max(0, _compute_border_thickness(...))
守卫2（断言）：assert border_bands_thickness >= 0, f"边框厚度异常: {border_bands_thickness}"
```

- 守卫 1 兜底：任何公式计算的负值强制归零，避免崩溃
- 守卫 2 报错：DEBUG 模式下保留断言以便日志追溯（用户正式版本通过 AST 扫描已关闭断言）

### 验证
同一 1000 组随机参数再跑一次：崩溃 0 件 ✅；3 个负厚度案例被正确截断为 0（日志记录 `WARN: border thickness -2 clamped to 0`），间隙层分类失败案例已记入 bug 清单（后续专项修复）。

## 问题三：圆角裁剪工具输出文件名逻辑（`67d3cac`）

### 现象 1：多图批处理覆盖
批处理 3 张素材（同图案同尺寸同圆角），原逻辑输出 3 个同名文件，第 2、3 张依次覆盖第 1 张，用户最终只拿到 1 张结果图。

### 现象 2：横版竖版宽高顺序写反
横版目标图（65×115cm，W=115 H=65，宽>高）写成 `克罗印花_65x115_r3cm.jpg`，竖版图（50×160cm，W=50 H=160，高>宽）也写成 `花漾之约_50x160_r3cm.jpg`。宽高**没有按方向排序**，用户无法从文件名识别横竖版。

### 修复（gui/cropper_panel.py，106 → 66 行）
**统一函数 `_build_output_filename(idx=None, total=None)`**：
1. **宽高按方向排序**：横版 (W≥H) → `{W}x{H}`；竖版 (H>W) → `{W}x{H}` 但在开头加 `竖版_` 前缀（如 `竖版_花漾之约_50x160_r3cm.jpg`）
2. **批处理序号后缀**：当 `idx is not None`（批处理模式），追加 `_idx{idx}` 后缀（`_idx1` / `_idx2` / `_idx3`），保证多文件不覆盖
3. **圆角单位统一**：圆角 r 值带单位 `cm`，整数不写 `.0` 小数（r=3→`r3cm`，r=3.5→`r3.5cm`）

### 验证
| 场景 | 原文件名 | 新文件名 |
|---|---|---|
| 横版单张 65×115 r=3cm | `克罗印花_65x115_r3.jpg` | `克罗印花_115x65_r3cm.jpg` |
| 竖版单张 50×160 r=3.5cm | `花漾之约_50x160_r3.5.jpg` | `竖版_花漾之约_50x160_r3.5cm.jpg` |
| 批处理 3 张同参数 | ×3 覆盖 1 文件 | `..._idx1.jpg` / `_idx2.jpg` / `_idx3.jpg`（3 份独立）|

全部通过 ✅

## 问题四：圆角裁剪工具匹配已经裁剪图的问题（`3dca946`）

### 现象
用户把"已经裁过圆角的旧成品图"再次导入裁剪工具，模板匹配器误匹配到素材库中"花纹相似但四角完整的其他图案"。原因：已裁剪图的四个角为圆弧（白色扇形区），全图像素相似度计算时圆弧区拉低分数，反而让「方向错误但花纹近似的其他素材」得分更高。结果：旧成品被裁两次，圆角 3cm 变成 6cm，边角损坏。

### 根因（模板匹配逻辑未区分「未裁剪原图」vs「已裁剪成品」）
`template_matcher.py::_match_template` 只输入「目标图」但不判断它是否已经是裁过圆角的图。若目标图本身含圆角圆弧，任何"完整四角原图"的相似度都会被圆弧惩罚项拉低，最终匹配混乱。

### 修复
**新增 `_detect_already_cropped(target_img, estimated_r_cm=3)`**，在模板匹配前置检测：
1. **扇形 ROI 取色**：四个角各取一个扇形区，半径 = `(估算 r_cm × px_per_cm) + 3px`（略大于实际圆角半径，确保覆盖完整圆弧）
2. **白色占比判定**：扇形区内「像素亮度 > 240（接近纯白）」的占比 > **80%**，标记为"圆弧白区候选"
3. **边缘方差判定**：扇形区外 5px 边界带灰度方差 < **15**（圆弧边缘平滑，无尖锐棱角），标记为"圆弧平滑候选"
4. **综合判定**：4 个扇形中 ≥ **3 个** 同时满足两项条件 → 判定为「已经裁剪过圆角图」，**跳过模板匹配**，直接走"用户自定义裁剪尺寸"模式
5. **UI 提示**：检测到已裁剪图时，cropper_panel 状态栏显示黄色提示「⚠️ 检测到已裁过圆角，跳过自动匹配，请手动设置尺寸」

### 验证
| 图集 | 总数 | 真阳性（已裁→检出） | 假阳性（未裁→误报） |
|---|---|---|---|
| 已裁圆角图集（20 张手工裁剪） | 20 | **19 / 20（95%）** | - |
| 素材库原图（100 张） | 100 | - | **2 / 100（2%）** |
- 1 张漏检：边角为特殊米黄色背景（亮度 ≈ 220 < 白色阈值 240），被判定为"非圆弧"。用户手动设尺寸即可，不影响功能
- 2 张误报：原图自带大面积白色装饰扇形边（蔓生花），形态接近圆弧。UI 有提示但用户可手动点"匹配素材"按钮覆盖

准确率足够生产使用 ✅

## 经验教训
1. **sentinel 层与 clip 裁剪的顺序是陷阱**：任何多层 mask 构建，必须遵循"先全部画内容 → 再统一 clip"的顺序。反向会导致 sentinel/参考层像素被误裁，下游取色逻辑出现随机且极难定位的偏差
2. **fuzz 测试是安全性约束的廉价来源**：1000 组随机参数（2 分钟跑完）就能发现 3 组负厚度崩溃，成本远低于人工设计边界案例。建议所有几何计算函数定期跑 fuzz
3. **"已经裁过"检测应是所有图像工具的前置守卫**：裁剪工具、变形工具、滤镜工具的输入端必须能识别"上一轮工具的输出图"，否则二次处理不可逆损坏素材。扇形 ROI 白占比 + 方差双指标是轻量有效的检测手段
4. **文件名是用户的第一索引**：横版竖版前缀、批处理序号、单位统一三项，看似小事，但用户翻文件夹时能节省大量排序时间。GUI 输出务必标准化命名
