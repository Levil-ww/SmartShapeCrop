一、结论先行

不建议对这个项目做「重构」，建议做「定点手术 + 防腐层」。

本项目已具备三个稀缺条件：444 个用例全绿（74 秒可复跑）、core 层无 GUI 反向依赖、算法实现质量高于同类内部工具。 在这种底子上做大规模重构，收益有限而回归风险真实——项目历史上已多次出现「重构引入回归」的记录。 真正值得投入的，是先把三处会持续放大的结构性问题定点清除，再建立防止回流的口子。

三、六项结构性事实（含证据）

F1 · 存在 1 处循环依赖闭环，被延迟导入掩盖 高

三处导入构成闭环，其中一条边刻意写在函数体内，使模块级静态图看不出环：

core/lshape_border.py:34
    from .image_cropper_mask import _estimate_outer_background      ← 模块级

core/image_cropper_mask.py:14
    from .image_ops import load_image_rgb, fit_image_to_rect        ← 模块级

core/image_ops.py:1186   （位于 render_design() 函数体内，缩进 12 空格）
    if _do_completion:
        try:
            from .lshape_border import apply_lshape_border_completion   ← 函数级，打破闭环

为什么这条重要：它不是「洁癖问题」，而是一个重构陷阱。任何人日后把 image_ops.py:1186 这行「提纯」到文件顶部（这是最自然的整理动作），模块导入立刻变成真循环并抛 ImportError，程序无法启动。反过来，如果按 F2 的建议拆解 render_design()，这个函数级导入也会随之移位——必须在动刀前先解掉环，而不是拆完再发现。

根因：lshape_border 依赖的是 image_cropper_mask 里一个下划线开头的私有工具函数 _estimate_outer_background。封装泄漏 + 工具函数放置层级不当，共同制造了这个环。

请注意最后两列的组合规律：单洞路径、多洞路径、L 形路径的处理逻辑被物理交织在同一个函数体里，靠 if mode == ... 与护栏变量区分。 注释里的 PURE ADD-ON GUARD、原单洞/椭圆/L 形代码一字未改 这类标记，说明开发者自己也知道这是在不破坏既有逻辑的前提下硬塞进去的——这是理性选择，但代价已经积累到 848 行。

为什么这是最高优先级的靶点：它是导出路径（用户点「导出 JPG」走的就是它），一旦出错是用户可见的成品事故；同时它没有任何单元测试直接测内部阶段，现有测试多数只断言「不崩溃 + 尺寸非空」。这意味着它是当前收益与风险比最差、但改动频率最高的区域。

F3 · 水池设计器面板拆成 6 件套后，耦合并未下降 中

gui/property_panel.py 已拆为 6 个子模块（dialogs / generate / layers / poolbox / widgets / workers）。 文件确实变小了，但依赖关系没有形成边界，实测两点：

  1. 子模块之间存在 11 条横向依赖边，且形状高度规律： 
    property_panel_generate  ->  dialogs, widgets, workers
property_panel_layers    ->  dialogs, widgets, workers
property_panel_poolbox   ->  dialogs, widgets, workers
lshape_panel             ->  widgets, workers
    widgets 被 5 个模块引用、workers 被 5 个引用、dialogs 被 4 个引用。 它们事实上是共享区而非独立模块——却仍然挂在 property_panel_* 这个前缀下，被当作「水池设计器的内部部件」。连 L 形挖角面板（另一个业务模块）也要来借用它们。
  2. 每个子模块都拉取同一套 core 依赖。6 个子模块中有 5 个都重复导入 core.app_settings、core.geometry、core.parser.name_parser、core.parser.template_matcher、core.pool_designer、core.pool_designer.sketch_parser 这一整组。 这说明拆分是按代码块切的，不是按职责切的——读者仍然无法从某个子模块的导入头判断「这个模块到底干什么」。

一个需要注意的对照：它们的逐行相似度只有 8.4%。所以这不是复制粘贴造成的，不能用「去重」解决。 这是「拆了文件、没拆职责」的典型形态——机械拆分能降低单文件行数，但不会自动降低耦合。

F4 · 5 份打包脚本是真正的复制粘贴：相似度 93.3% 中

packaging/ 下有 5 份打包入口（package.py、packageV2.0.py、packageV2.1.py、legacy/packageV2.1.2.py、packageV2.2.py）， 实测 V2.1.2 与 V2.2 的对比结果： 

逐行相似度          93.3%
完全相同代码行       363 行 / 400 行
最长连续相同块       206 行
跨文件同名函数       13 个

13 个同名函数：_print_step、_fail、parse_args、check_resources、_get_pyinstaller_version、 ensure_pyinstaller、clean_build、_build_cmd、_run_build、build_exe、show_result、 _dir_size_mb、_find_tesseract_install。

这是全项目性价比最高的重构点：它与业务逻辑完全隔离（打包失败不会污染用户功能）、有明确的「产物能出包」验收标准、且改动量小。 唯一的真实成本是必须用新脚本成功出一次包来验证——而本机 .venv 内 PyInstaller 缺失（既有报告 P0-02 已记录），所以这项工作应排在补装工具链之后。

F5 · 7 步法与 9 步法是「概念重复」，不是「代码重复」 中

草图识别有两条流水线：sketch_parser.py 的 _7step_parse()（348 行，单洞）与 sketch_parser_multihole.py 的 _9step_multi_hole_parse()（411 行，多洞）。两者共享同一套步骤命名与辅助概念， 但实测： 

整文件逐行相似度      8.5%
完全相同代码行         85 行 / 1,491 行
最长连续相同块         14 行
这个数字改变了处理方式 相似度只有 8.5%，说明它们各自独立实现，不是复制出来的。因此不能走「保留一份、删除另一份」的合并路线——那等于重写一条流水线。 真正的问题在另一层：两者重复了同一批概念——_progress、_try_assignment、_round_pref_bonus / _round_pref_bonus_multi 各写一遍， 意味着同一个业务规则改动需要在两处分别修改，且没有测试保证两处行为一致。

务实的处理：不合并流水线，而是先抽出共用的概念层（步骤进度上报、数值分配打分、圆整偏好），让两条流水线调用同一份实现。 这样既消除了双份维护，又不必承担「重写 OCR 主流程」的风险。

作为对照：core/ 全部约 17,600 行、gui/ 约 6,900 行、tests/ 约 6,200 行。 也就是说 scripts/ 的体量约等于 core + gui 之和。

为什么它会在重构中被低估：这些脚本大量直接引用 core 的内部符号（core.corner.algorithm、core.image_cropper_border 等）， 其中 core.image_cropper 一个模块就被引用了 93 处。它们不在测试套件里、不进 CI，所以任何 core 的 API 调整都不会被测试拦住， 只会在下次有人跑诊断脚本时静默失效。scripts/ 是重构时隐形的约束网。

四、先圈定「不该动」的部分

重构建议若是只讲「哪里该拆」，执行时很容易误伤核心。用扇入数据（被多少个模块依赖）先把稳定资产标出来：

扇入模块定位
93core.image_cropper裁剪服务主入口，全项目被引最多 → 冻结契约
58core.config集中配置单一来源，收敛方向正确 → 冻结契约
47core.pool_designer.sketch_parser草图识别入口 → 保持签名
44core.geometry参数化形状定义 → 冻结契约
39core.corner.algorithm圆角 mask 算法，三入口统一委托 → 冻结契约
34core.image_ops渲染总入口（同时也是 F2 的靶点）→ 只拆内部，不改签名
读法 扇入越高，说明「改它的成本」被放大的倍数越大。上表六个模块的共同处理原则是：只允许新增、不允许修改既有函数签名与返回语义。 对 core.image_ops 的特殊之处在于——它既要保持对外签名不变，内部又急需拆解，因此它的重构必须走「内部提纯 + 外部冻结」的双轨。

五、重构建议（按风险从低到高分四档）

排序原则：先建立可验证的安全网，再做零功能风险的整形，最后才动核心逻辑。前两档可以在完全不改变程序行为的前提下完成。

第 0 档 · 护栏先行 不做这一步，后面每一档都在赌博

0-1　把 444 基线固定为可复跑的标尺

现状：实测 444 passed in 74.08s，退出码 0，安全网确实可用。
动作：在动手前记录一次基线（用例数 / 耗时 / 退出码），此后每个批次改动后复跑比对。任何一次不是「444 passed」都立即回滚，不继续下一批。
验收：基线快照留档，且注明取证日期；README 中的测试数字与本机实测一致。

0-2　为 render_design 建「黄金样本回归」——本报告最重要的一条建议

问题：现有对 render_design 的 17 处调用几乎都只断言「不崩溃 + 尺寸非空」，没有像素级基线。这意味着 F2 描述的 848 行拆解当前不可验证——拆坏了也测不出来。
动作：不改动任何渲染代码，用现有素材跑若干代表性 CropDesign（矩形嵌套 / 椭圆 / L 形 / 多洞，各含与不含带框素材的变体），把输出图存为基线文件；新增一个比对用例，断言新输出与基线的像素差异在容许阈值内。
为什么值得：它是唯一能让 848 行函数变成「可安全拆解」的手段。成本是写一个脚本 + 存几张图，收益是把整个第 3 档从「高风险」降为「可控」。
注意：基线图不进版本库（项目已有 81 MB 图片与 90 MB 误跟踪内容的先例），放本地或单独目录并加忽略规则。
第 1 档 · 零功能风险的整形 不触碰业务逻辑，可与日常改动并行推进

1-1　packaging 抽公用模块（对应 F4）

动作：把 13 个重复函数抽为 packaging/_common.py，各版本脚本只保留「版本差异部分」（hiddenimports 清单、spec 名称、Tesseract 内嵌开关）。旧的 4 份归档，只留 packageV2.2.py 作为唯一入口。
验收：用抽取后的脚本成功出一次包，dist/ 产物的时间戳 ≥ 最新源码时间戳。
前置：本机 .venv 缺 PyInstaller，需先补装（既有报告 P0-02）——这也是当前项目「所有改进都发不出去」的根因。
风险：极低，与用户功能完全隔离。

1-2　scripts/ 分级归档（对应 F6）

动作：按「是否对应已修复缺陷」把 185 个脚本分三级——已闭环的一次性诊断脚本移入归档；仍在用的保留并补一句用途说明；确认无人引用的可删。先只出分级清单，不移动。
收益：把重构时的「隐性约束网」显性化。在动 core 之前就知道哪些脚本会被波及。
纪律：清单先给你确认，确认后再执行——不直接动手。

1-3　兼容层迁移收尾（对应 compat 层）

现状：core/compat/ 的 sys.modules 别名机制设计规范、文档完备。但仍有活跃调用点未迁移——例如 gui/property_panel_layers.py:398 使用旧路径 from core.psd_loader import ...，tests/core/test_rounded_corner.py 也仍从 core.rounded_corner 导入。
动作：把这些调用点改到新路径（core.psd.loader / core.corner.algorithm），全部迁移完成后 compat 层即可整体退役——按它自己的文档说法，「删除本子包即可，无需改动业务代码」。
收益：消除一类「看起来存在、实际是别名」的幽灵模块，让依赖图可信。同时避免打包 hiddenimports 长期为一个不存在的路径做白名单。

1-4　未使用导入与仓库卫生

既有报告 P1-01（250 处未使用导入）与 P2 第 1–3 项（重复 spec、调试残留、旧脚本归档）均属此类，此处不重复展开。唯一补充：必须先清理未使用导入，再做依赖图分析——否则 import 头失真会掩盖真实的分层问题（F1、F3 都曾因此被误判）。
第 2 档 · 结构修复 改变模块边界，不改业务行为；每项都需跑 444 基线

2-1　解掉循环依赖闭环（对应 F1）

动作：把 _estimate_outer_background 从 image_cropper_mask 下沉到一个更基础的层级（与 _estimate_* 同类工具函数放在一起），使 lshape_border 不再反向依赖裁剪 mask 模块。环解开后，image_ops.py:1186 的函数级导入才有资格改为模块级。
关键：顺序不能反。必须先解环，再提纯导入。反过来做会直接 ImportError。
验收：444 基线不变；且在修改后做一次「冷启动」验证（清 __pycache__ 后 python main.py 能起来），确认没有隐性导入顺序依赖。
风险：中——涉及 _estimate_outer_background 的全部调用点，需逐一比对。

2-2　为 property_panel 建立一个真正的共享契约层（对应 F3）

动作：把被 5 个模块共用的 widgets / workers / dialogs 提升为独立于「水池设计器」的共享模块（例如 gui/shared/ 或直接与面板平级），让 L 形挖角面板引用共享模块时不再是「借用别人的内部件」。
不建议：不要试图把 6 件套重新合并回一个大文件——那只是把问题藏回去。也别期望这一项能显著降低耦合：拆分的价值在于让依赖方向变清晰，不在于减少行数。
验收：6 件套的 11 条横向依赖边中，指向共享区的部分变为「单向依赖共享层」；GUI 56 个用例保持全绿。
风险：中——GUI 层改动面较广，建议单独一次改动、不与其他项混做。

2-3　抽出草图识别的共用概念层（对应 F5）

动作：不改动两条流水线的算法，只把重复的概念抽为共用函数——步骤进度上报、数值分配打分（_try_assignment）、圆整偏好（_round_pref_bonus）。让 _7step_parse 与 _9step_multi_hole_parse 调用同一份实现。
明确不做：不合并两条流水线。8.5% 的相似度说明它们本就不同，强行合并等于重写 OCR 主流程。
验收：两条流水线的既有用例（tests/sketch/ 共 4 个文件）全绿；抽出前后对同一批草图输出的识别结果逐字段一致。
风险：中——OCR 结果对数值路径敏感，务必做识别结果一致性比对，只看测试绿不绿不够。
第 3 档 · 高风险手术 仅在完成第 0 档后才有资格启动；且必须逐块进行

3-1　把 render_design() 从「挂载点」改造成「流水线」（对应 F2）

目标形态：函数体只保留阶段编排，各挂载块提取为独立阶段函数，按 F2 表格中的 10 个块归并为若干策略：
  1. 素材适配与方向校正（现有步骤 0–2）
  2. 基础形状渲染（矩形 / 椭圆 / L 形主体）
  3. 多洞处理（PRE-COMPUTE → APPLY → 独立素材填充）
  4. 边框补全（L 形边框三级路由 + 统一黑框兜底）
  5. 残留清理（单洞 Stale-Decor 系列 + 接缝羽化）
方法与硬约束：
  • 一次只搬一个块，每搬完一块立即跑黄金样本比对 + 444 基线，不绿就回滚；绝不「一天搬完 5 个块」。
  • 对外签名零变化：render_design(design, quality=...) 的参数、返回、（以及 render_design_lod 等兄弟入口）一律不动——它的扇入是 34，动签名会连锁波及 GUI 与测试。
  • 搬块时顺带保留原有的 [Fix 日期] 注释。这些注释是缺陷溯源的唯一线索，本项目在这方面做得很好，不要在重构中丢掉。
验收：黄金样本像素级一致；444 基线不变；render_design 本体降到可阅读的行数（目标 < 150 行）。
风险：高——这是全项目改动风险最高的区域。没有第 0 档的黄金样本，就不应启动这一项。

3-2　其余长函数的「顺手提纯」

除 render_design 外的 23 个 ≥200 行函数（_extract_direction_label_numbers 747 行、_detect_lshape_geometry 574 行、worker.run() 515 行等），不建议专门立项。
建议做法：维持既有报告 P1-04 的结论——只在因业务需要改动某个函数时，顺手把其中一段边界清晰的逻辑抽成带 docstring 的私有函数，并为它补一个直接用例。为拆而拆的收益远小于回归风险。

六、明确不建议做的

动作不建议的理由
推倒重写 / 换架构 项目有 444 个用例、算法实现经过多轮真实案例锤炼（圆角多层边框、OCR 稳定性投票、剖面扫描）。重写等于放弃这些已验证的复杂度沉淀，而它们恰恰是这个工具最难的部分。
把 6 个 GUI 子模块重新合并 合并只是把问题藏回大文件。F3 的问题是「缺共享契约层」，不是「文件太多」。
合并 7 步法与 9 步法流水线 实测相似度仅 8.5%，本质是两条不同实现。合并 = 重写 OCR 主流程 = 放弃现有识别精度。
为了拆 848 行而先拆 848 行 在没有像素级基线的前提下拆解导出路径，是在用用户的成品做测试。先做 0-2，再谈 3-1。
把多项改动合进同一次提交 项目历史已多次记录「重构引入回归」。单点修改 → 立即复跑 444 基线 → 再动下一处，是本项目被反复验证过的唯一安全节奏。

七、执行纪律（若决定推进）

  1. 单批次单主题。一次改动只解决一个编号项，禁止「修崩溃 + 清导入 + 拆函数」混做。
  2. 每批次三重验证。① 444 基线全绿；② 涉及渲染时跑黄金样本像素比对；③ 目的是导出路径时，在打包版 exe 上做一次端到端冒烟（L 形挖角目前仍是待验证项）。
  3. 保留注释溯源。所有 [Fix 编号 日期] 注释在重构中随代码搬移，不得删除——它们是唯一能区分「已修 / 未修」的线索。
  4. 顺序不可颠倒。先护栏（第 0 档）→ 再整形（第 1 档）→ 再改边界（第 2 档）→ 最后动核心（第 3 档）。其中 2-1 必须在 3-1 之前（否则循环依赖会在拆解时爆开），1-4 必须在依赖分析之前（否则 import 头失真会误导判断）。
  5. scripts/ 分级清单先确认再执行。按项目一贯约定，涉及文件移动/归档的操作，先出清单、经审阅后再动手。

八、需要你确认的三个决策点

1. 重构的目标是什么？这决定了优先顺序：

  • 目标是「交付稳定、少出事故」 → 只做第 0 档 + 第 1 档，第 3 档无限期搁置。
  • 目标是「后续加功能更快」 → 重点在第 2 档（解环 + 共享层），这是新增功能的主要摩擦点。
  • 目标是「准备一个大版本」 → 才值得投入第 3 档，且必须先完成黄金样本。

2. 是否允许改变程序行为？本报告的方案按「行为完全不变」设计。若允许微调行为（例如顺手修掉 P0-01 的 dpi 崩溃），可以与重构批次并轨，但验证标准需相应加强。
