一句话结论

值得做，建议按「保守方案 A」分批推进。 拆分的本质是「把一组控件及其状态从 PropertyPanel 搬到独立 QWidget， 再通过信号委托把操作转发回 PropertyPanel 的同一套实现」—— 这正是 L 形面板已验证过的路径。 唯一需要人为克制的是：不要顺手重构 _collect() 那 190 行坐标换算代码， 那属于功能改动，与「不能改变程序功能逻辑」的约束直接冲突。

2. 现状：多洞 UI 的挂载方式

2.1 单洞与多洞当前混在同一面板

水池设计器的多洞参数区（_gb_multihole）并不是一个独立区域， 它是追加在 PropertyPanel._inner_layout（水池抽屉）末尾的一个 QGroupBox，靠 hide() / show() 切换： 

# gui/property_panel.py  L197 / L285-286
self._gb_multihole = QGroupBox("多洞参数（厘米）")
...
self._set_multi_hole_row_visibility(0)
self._gb_multihole.hide()          # 启动时默认隐藏（单洞模式）
self._inner_layout.addWidget(self._gb_multihole)

也就是说：单洞/多洞共用一个面板、一套 design、一条生成链路， 仅靠可见性开关区分。这正是本次要拆的根。

2.2 多洞 UI 的构成

4. 参照范式：L 形面板拆分

这是本次拆分的模板。 gui/lshape_panel.py 已经完整验证了「Mixin + 信号委托」这条路： 子面板保留自己的 UI，所有业务操作通过 pyqtSignal 委托回 PropertyPanel 的同一套实现， 子面板内没有任何重复的渲染逻辑。

4.1 L 形的桥接契约（可直接复用的形态）

# main.py —— 创建两个面板后注入
self.lshape_panel = LShapePanel()
self.panel.set_lshape_panel(self.lshape_panel)   # 注入引用 + 连接信号

# gui/property_panel.py L421 —— 注入入口
def set_lshape_panel(self, panel) -> None:
    self._lshape_panel = panel
    panel.lshape_params_changed.connect(self._on_lshape_params_changed)
    panel.lshape_applied.connect(self._on_lshape_applied)
    panel.generate_requested.connect(_lshape_run_generate)   # 委托到 _pool_run_generate
    panel.save_requested.connect(self.save_requested.emit)   # 导出走既有流程
    panel.sketch_pick_requested.connect(lambda: self._pool_pick_sketch(source='lshape'))
    ...

5. 关键决策：_collect() 的两种搬法

这是整个改造中唯一需要你拍板的技术选择。两种搬法功能等价性风险差异明显：

方案 A · 保守190 行留在 _collect()，只改数据来源推荐
做法
_collect() 内的坐标换算代码一行不动， 仅把「读哪个 SpinBox」改成先从新面板取一个值快照： 
# 改造前
wv = self._mh_sp_hole_w[i].value()
# 改造后（仅此一行变化）
wv = _mh_vals['holes_wh'][i][0]
其中 _mh_vals = self._multihole_panel.get_raw_values()。
优点
坐标算法、素材继承、layout 三分支一行不改； git diff 只涉及「数据来源」这一个概念， 回归面极小，与「不能改变功能逻辑」的约束最贴合。
代价
新面板不持有完整业务逻辑（仅持有 UI 与状态）。但这不构成问题 —— L 形面板同样不持有渲染逻辑。
方案 B · 彻底190 行整体搬进新面板不建议本次采用
做法
把 L167–356 整体迁入 MultiHolePanel.build_hole_dicts(design)， _collect() 只调一行。
优点
职责最干净，新面板自包含。
缺点
移动 190 行密集数值代码，需逐一验证 horizontal / vertical / mixed 三个分支 + 四个闭包的三重 fallback 行为完全一致， 回归风险显著高于方案 A。
结论
方案 B 属于「顺手重构」，与本次约束相抵触。 建议列为后续独立任务，不并入本次拆分。

7. 零功能变更保证措施

  • core/ 零改动 —— 多洞几何算法（geometry.py / image_ops.py / sketch_parser_multihole.py）本次完全不碰
  • 状态变量唯一归属 —— _mh_active_count 等全部迁入新面板，PropertyPanel 只通过 API 读，不再自己维护副本
  • 信号委托不复制逻辑 —— 新面板「生成预览」必须转发到 _pool_run_generate(source='pool')，不新建渲染链路（L 形面板就是这么做的，其内部无任何重复渲染代码）
  • 返回值结构冻结 —— get_multihole_params() 必须返回与现 _detect_multihole_edits() 完全相同的 dict 结构，PoolRenderWorker 侧零改动
  • _collect() 坐标算法零改动 —— 方案 A 只换数据来源，不换算法
  • 交互范式保持 —— 多洞 SpinBox 的 valueChanged 已于 2026-09-05 全部 DISCONNECTED，改为手动生成按钮驱动；拆分后不得恢复实时渲染连接
  • 静默失败包装保留 —— _collect() 与 _detect_multihole_edits 的 try/except 容错语义原样保留
  • 可验证证据 —— 完成后提供 git diff --stat 输出 + 渲染比对图
