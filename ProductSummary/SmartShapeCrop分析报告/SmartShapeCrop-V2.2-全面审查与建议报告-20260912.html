二、P0 级问题（阻塞发布）

三项均直接影响可用性或发布能力，建议在下次出包前全部处理。

P0-01
主窗口状态栏对 IFDRational 类型格式化崩溃 —— 今晨发生 3 次 上传带 EXIF 分辨率标记的图片即触发，必现
现状
main.py:307 用 f"{...:.0f}" 直接格式化 img.info['dpi'][0]。当该图来自 Image.open()（JPEG 含 EXIF 的 XResolution/YResolution）时，PIL 返回的是 IFDRational 而非 int，该类型不支持任何格式说明符，抛 TypeError。
证据
崩溃时间: 2026-09-12 09:46:55
Traceback (most recent call last):
  File "F:\SmartShapeCrop\main.py", line 307, in _on_rendered
    self._status_size.setText(f"画布尺寸：{img.width} × {img.height} px (... @ DPI {img.info.get('dpi',(150,))[0]:.0f})" ...)
                                                                                                      ^^^^^^^^^^^^^^^^^
TypeError: unsupported format string passed to IFDRational.__format__
同一根因在 crash.log 中记录 3 次（09:46:55 / 09:47:12 / 09:59:15）。机理复现（Pillow 12.3.0）： 
IFDRational(300,1) 类型 = IFDRational
  format(r, ''    ) -> OK 值='300.0'
  format(r, 'd'   ) -> *** TypeError
  format(r, 'f'   ) -> *** TypeError
  format(r, '.0f' ) -> *** TypeError
带 EXIF 分辨率的 JPEG -> info["dpi"] = (300.0, 300.0)，元素类型 = IFDRational
  *** 格式化 :.0f 崩溃：与 crash.log 记录完全一致
影响
触发路径是两条日常操作：main.py:331 _on_sketch_loaded（上传草图）与 main.py:314 _on_cropped_image（裁剪回填），二者都把 Image.open() 的产物 emit 给 _on_rendered。用户只要上传一张相机/手机拍摄的、或经微信/PS 处理过并保留了 EXIF 分辨率的图片，状态栏刷新即抛异常。

异常从 Qt 槽函数抛出后经 sys.excepthook（main.py:507）写入 crash.log；而 PyQt5 对槽内未捕获异常的标准处理是中止进程。这与项目长期追查的 0xC0000409 属于同一类失败模式——此前排查聚焦于 QThread 生命周期，本路径是独立且更易触发的一条。

另一个观察：项目自有 204 张图片无一例外 dpi 为 IFDRational（都是程序生成的图，dpi 为 int），所以靠项目内素材永远复现不出来——这解释了它为何能长期潜伏。
建议
与 core/image_ops.py:1697-1701 的既有防御口径保持一致（那里已经写好了正确的处理）： 
# 推荐：与 save_jpg 完全同源
_dpi = img.info.get('dpi')
if _dpi:
    _dx = float(_dpi[0]) if isinstance(_dpi, (tuple, list)) else float(_dpi)
    _dy = float(_dpi[1]) if isinstance(_dpi, (tuple, list)) and len(_dpi) > 1 else _dx
else:
    _dx = _dy = 150.0
self._status_size.setText(f"画布尺寸：{img.width} × {img.height} px "
                          f"({img.width/_dx*2.54:.1f}cm × {img.height/_dy*2.54:.1f}cm @ DPI {_dx:.0f})")
顺带修掉两个同源隐患：'dpi' in img.info 只判存在、不判类型与长度，若 dpi 是单值（非序列）则 [1] 会抛 IndexError 或 TypeError；建议一并加类型兜底。

P0-03
433 个测试全绿，却拦不住一个必现崩溃 —— GUI 测试网存在结构性盲区 测试断言的是「信号已接线」，而非「槽函数能跑通」
现状
tests/gui/test_main_window.py 对 _on_rendered 的验证方式是 assert_signal_connected(...)——只断言「rendered 信号连接到了 _on_rendered」，从未真正构造一张图调用它。因此函数体内的格式化逻辑处于零覆盖状态。
证据
tests/gui/test_main_window.py:97-98： 
        assert_signal_connected(
            main_window.canvas.rendered,
            main_window._on_rendered,
            'PreviewCanvas.rendered -> MainWindow._on_rendered',
        )
全 tests/ 目录检索 _on_rendered，仅命中上述 2 行（另一处为 test_signals_contract.py 的信号名清单），没有任何测试真正传入 PIL 图像调用该槽。
影响
测试的「接线正确性」覆盖得很好（这本身很有价值，能抓到「点了没反应」类静默失效），但槽函数体的执行路径完全裸奔。P0-01 之所以能长期潜伏并在今晨连撞三次，正是因为这个盲区——它同时也意味着其他槽函数体内可能存在同类隐患。
建议
为「槽函数体」补一组行为用例，而非仅仅接线用例。以本问题为例，用已有夹具即可写出来： 
def test_on_rendered_accepts_exif_rational_dpi(main_window):
    """回归 P0-01：带 EXIF 分辨率的图片不得让状态栏刷新崩溃。"""
    from PIL import Image
    from PIL.TiffImagePlugin import IFDRational
    img = Image.new('RGB', (100, 60))
    img.info['dpi'] = (IFDRational(300, 1), IFDRational(300, 1))
    main_window._on_rendered(img)          # 修复前必抛 TypeError
    assert 'DPI' in main_window._status_size.text()
该用例成本极低、价值极高：它是唯一能在测试阶段拦住 P0-01 的手段。建议同时盘点其余「纯格式化/纯计算」型槽函数，按同一模式补齐。

八、结论

SmartShapeCrop V2.2 是一个功能完整、算法扎实、工程习惯良好的项目。433 个用例全绿、40/40 打包白名单无漏收、线程退役双通道闭环、失败掩盖已消除、core 层分层基本干净——这些都经过了本次逐行核实，不是沿用历史结论。

本次审查的核心增量是推翻了「崩溃未复发」的判断：crash.log 中今晨三次崩溃指向一个必现的 IFDRational 格式化缺陷，且项目自有素材永远复现不出（204 张图的 dpi 全为 int），只能靠用户上传的外部图片触发。它之所以能穿过 433 个测试，是因为 GUI 测试断言的是「信号已接线」而非「槽函数能跑通」——这是本次最值得修复的结构性问题，而不只是修一行代码。

另一处需要正视的是交付链条：产物落后于源码、打包工具链缺失，使得任何改进都无法到达用户。建议把「P0-01 修复 + 回归用例 + 重新出包」作为一组最小闭环一起推进——只修代码不出包，等于没修。

预期 完成第一阶段的四项后，项目将回到「可交付且崩溃窗口关闭」的状态，综合健康度预期从 64 升至 82。剩余 P1/P2 属于持续降本，不构成发布阻塞。
