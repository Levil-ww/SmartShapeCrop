1执行摘要

一句话结论 + 五个关键数字

核心判断 V2.1.2 目前处于 「功能狂奔 → 质量欠账」 的临界点： 9 月 3 日单日 18 次提交把 L 形挖角推到了新能力高度（边框补全、损耗回传、串台修复）， 但零文档归档、测试出现 4 项红灯、6 个后台线程无人接管。 功能本身是健康的，失守的是工程纪律。V2.1.2 剩余方向应当从「加功能」切换到「收敛质量 + 补齐契约」， 把一个能跑但脆弱的版本，固化成一个敢交给用户天天用的版本。

✅ 值得肯定的地方

  • 架构分层干净：core/ 零反向依赖 gui/，业务与界面边界守得住。
  • 配置有单一来源意识：core/config.py 已集中管理 331 行常量，方向正确。
  • 线程范式已被正确验证过一次：canvas_widget.py:231-252 的 _retire_worker 是标准答案（requestInterruption → wait → deleteLater）。
  • 向后兼容层设计考究：core/compat/ 用 sys.modules 别名让旧导入路径零成本迁移，同源性有校验。
  • 文档资产极丰富：94 份 ProductSummary 记录了完整的决策脉络，在同类内部工具中罕见。

⚠️ 需要立刻止血的地方

  • 测试契约失守：4 项红灯，其中 3 项是 9/3 改了业务语义但测试未同步 —— 红灯亮了没人看见。
  • 线程退役只覆盖 2/8：main.py:454 的 closeEvent 只管渲染与导出线程，另外 6 个裸奔。
  • 主线程阻塞未根治：property_panel_generate.py:73 存在最长 30 分钟的 warmup.wait()。
  • 渲染层补丁叠加：render_design 632 行内塞了 5 个 Add-On 补丁，各自判定触发条件，无统一缓存失效契约 —— 这是「素材残留」反复修 5 次以上的根因。
  • 打包配置 7 份并存，spec 遗漏 core.lshape_border 的 hiddenimport。

3架构地图与分层健康度

依赖关系是否守规矩，是判断架构能否长期演进的关键

分层约束状态证据与说明
core 不反向依赖 gui 达标 全 core/ 无任何 from gui 导入，业务层纯净。这是本项目最值得保持的优点。
无循环 import 脆弱达标 image_cropper.py:14 ↔ image_ops.py 互相需要，当前靠「函数内延迟 import」打破环。 全项目函数内局部 import 达 11 处集中在 image_ops.py，属于结构性脆弱 —— 任何一次导入顺序调整都可能引爆。
模块间不访问私有成员 严重违规 sketch_parser.py:49-53 一次性 import 9 个下划线私有符号； image_cropper_border.py:57-61 连续 5 条； lshape_border.py:31-34 2 条。所谓"模块化拆分"实为物理切分，耦合未减。
UI 与业务分离 部分违规 main.py:277-301 有 22 处直读 panel._sp_w 等私有控件， _sync_panel_from_design 本质是 PropertyPanel 的私有 UI 逻辑被搬到 main.py，是重构残留。
数据模型纯净 违规 geometry.py:191 把 _cached_outer_image: Image.Image 作为 CropDesign dataclass 正式字段， clone()(248-258) 注释「共享只读引用，不复制像素数据」。大对象混入数据模型 + 共享引用 = "素材残留" bug 的架构级根因。
架构层面的核心矛盾：伪模块化 V2.1 把 property_panel.py 拆成 5 个 mixin、把 sketch_parser.py 拆成 6 个子模块， 但拆分方式是「把大文件物理切开，再用 import 私有符号把切口粘回去」。 结果是：文件数变多了，单文件行数下降了，但任何一处改动的影响半径和拆分前完全一样。 真正的模块化需要定义模块间的公共契约（哪些是 public API，哪些是内部实现）， 而不是靠下划线命名约定。这是 V2.1.2 及之后最值得投入的架构改造。

4P0 严重项：必须在 V2.1.2 内止血

4 项，涉及崩溃风险与工程纪律失守

P0-1后台线程退役只覆盖 2/8，6 个 QThread 裸奔

项目共有 8 个 QThread 子类，但只有 canvas_widget.py 的 2 个走通了标准退役范式。 关闭窗口时，其余 6 个线程没有接管者，导出大图（38MP 需数秒）途中关窗必然触发 QThread: Destroyed while thread is still running 崩溃 —— 而这个 bug 在 9/2 已经修过一次（F16），只是只修了 2 个。

  • main.py:454-465 closeEvent 只退役 _save_worker + canvas.shutdown()
  • 漏管：cropper._worker、cropper._match_worker、panel._pool_worker、 panel._sketch_parse_worker、panel._warmup_worker、lshape_panel._lshape_parse_worker
  • property_panel_poolbox.py:301 使用 warmup.terminate() —— QThread 的禁用手段，会在任意字节码处强杀
  • cropper_panel.py:971 直接 self._worker = None 丢弃引用，无 wait、无 deleteLater
  • property_panel_generate.py:73 warmup.wait(30 * 60 * 1000) —— 主线程最长阻塞 30 分钟
main.py:454-465 closeEvent 仅覆盖 2/8 线程
canvas_widget.py:231-252 _retire_worker —— 唯一正确的范式（requestInterruption → wait → deleteLater）
全项目 deleteLater 调用 仅 canvas_widget.py:247/250/252 三处，其余 Worker 零退役

建议：抽一个 WorkerManager 基类统一托管（注册 → 退役 → 超时降级）， 8 个 Worker 全部接入，main.closeEvent 只调一次 worker_manager.shutdown_all()。 预计 1–2 天，可一次性消除"关闭崩溃"这一类投诉。

P0-2测试契约失守：4 项红灯，3 项源于语义变更未同步

实测 pytest tests/：280 collected，4 failed。红灯本身不致命，致命的是红灯亮了没人发现 —— 9 月 3 日 18 次提交全部未跑测试，也无文档归档。

  • 3 项是业务语义有意变更，测试未同步（详见第 7 节）：挖角背景改白色、挖角损耗补偿取消、渲染语义调整
  • 1 项是测试硬编码路径过时：test_f5_f14_fixes.py 断言 F:\SmartShapeCrop\packageV2.1.py 存在，实际已移至 package/
tests/integration/test_pool_lshape_flow.py:73 期望挖角区显示材质，实际得到 array([255,255,255]) 纯白
tests/integration/test_pool_lshape_flow.py:179 assert 100.0 == 101.0 ± 1.0e-04（1cm 损耗补偿未生效）
property_panel_layers.py:87 注释明写"挖角值直接取草图识别的成品真值，不做额外损耗补偿"

建议：先由业务拍板（挖角到底该不该补 1cm 损耗 —— 印刷行业 1cm 误差是致命的）， 再决定改测试还是改代码。无论哪种，都必须让 pytest 回到全绿，并把「提交前跑测试」固化为习惯。

P0-3渲染层补丁叠加，缺少统一缓存失效契约

render_design（image_ops.py:548-1179，632 行）内部串联了 5 个 Add-On 补丁： Stale-Decor V1 / V2、接缝羽化、L 形边框补全、多洞 override。每个补丁各自判定触发条件，没有版本化的 invalidation key， 加上 CropDesign 数据模型里塞着 _cached_outer_image（geometry.py:191）并被多处共享引用。

这解释了为什么「素材填充残留」这一个 bug 在历史上被反复修了 5 次以上 （8.31 三次 commit、9.2 两次）：每次都是在打地鼠，没有一次触及根因。

image_ops.py:632 / 683 / 746 / 823 / 872 / 897 / 1005 / 1022 / 1104 / 1190 / 1503 11 处函数内局部 import
image_ops.py:576/579/627/633/681/702/723/800/806/1001 10 个互相耦合的 flag 变量（is_pool / has_outer_img 二次赋值 / lshape_cut_done / _sd_done …）
geometry.py:191 _cached_outer_image: Image.Image 作为 dataclass 正式字段

建议：把 5 个补丁收敛为 render_pipeline/ 的显式步骤， 引入渲染缓存 key（design 指纹 + 素材路径 + mtime），失效判定集中到一处。 这是「一次投入、永久止血」的改造，建议作为 V2.1.2 的核心技术任务。

P0-4主线程阻塞未根治，靠 processEvents 掩盖

property_panel_generate.py:162 的 _on_pool_finished_ok 作为主线程的槽函数， 却跑完整的素材库流程：全库扫描 scan_library、循环内多次 find_best_match、 主线程 load_image_rgb 读全分辨率 JPG。4 处 QApplication.processEvents()（L71/329/386/418） 只是让界面「看起来没死」，实为重入炸弹。

叠加 canvas_widget.py 的 LOD 渲染（每次参数变更主线程同步渲染，29MP 画布约 400ms/次， 当前靠 200ms 防抖缓解），用户感知就是「改个数字卡一下」—— 9/3 的 SpinBox 卡顿修复（fa23210）也只是缓解。

property_panel_generate.py:73 warmup.wait(30 * 60 * 1000) —— 30 分钟阻塞上限
property_panel_generate.py:329/386 循环内 processEvents，素材匹配 N 次全在主线程
canvas_widget.py 注释 L26-28 自述「原 ~100ms → 新 ~400ms」LOD 渲染耗时

建议：素材匹配与库扫描整体移入 Worker；LOD 渲染改为异步 + 中间态占位。 配合 P0-1 的 WorkerManager 一起做，可同时消除「崩溃」与「卡顿」两类用户投诉。
