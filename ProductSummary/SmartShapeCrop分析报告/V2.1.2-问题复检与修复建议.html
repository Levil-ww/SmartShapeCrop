2剩余 2 项红灯：一半过时、一半真 Bug

2.1 根因定位

两处失败都是同一个断言：期望挖角区等于洞色 (250,245,230)，实测 (255,255,255)。 代码在 core/image_ops.py:678-700：

# [Fix 2026-09-03] cut 区强制填纯白(255,255,255)：用户反馈原 hole_bg_color
#   (250,245,230 米色) 与素材底色过于接近，挖角视觉上不够明显。
#   白色也是 JPG 模式下表达"挖空/透明"的行业惯例（与 pool_hole_transparent=True 一致）。
cut_area_mask = np.array(full_inner_img, dtype=bool) & ~inner_mask
if cut_area_mask.any():
    canvas_arr[cut_area_mask] = 255   # ← 无条件硬编码

9/3 日志判定"这是有意的语义变更，测试未同步，不是 bug"。这个判断只对了一半。 关键问题在于：这行代码既没有读 design.hole_bg_color，也没有判断 design.pool_hole_transparent。

2.2 实测验证

构造同一份设计，只切换 pool_hole_transparent 开关，实测挖角区渲染结果：

同一个测试文件里，rect_hole 的用例（109-114 行）注释明确写着：

3.2 模板图缓存：素材残留的真根因 新发现

9/3 日志归因
geometry.py:191 把 _cached_outer_image 塞进 dataclass， 且 clone() 共享引用 → 改动影响半径大 → 素材残留根因。
本次实测结论
共享引用本身是安全的：adapt_pool_material 只读源图，PIL 操作返回新对象， np.array(canvas) 也是副本。真正的根因是缓存永不失效。

实测证据——全项目对 _cached_outer_image 的全部引用：

# 写入（生产代码仅此 1 处）
gui/property_panel_workers.py:610   design._cached_outer_image = cached_img
# 读取（生产代码仅此 1 处）
core/image_ops.py:575       cached_img = getattr(design, '_cached_outer_image', None)
# 声明与传递
core/geometry.py:191 / 253 / 257

# 失效/清除逻辑：生产代码中 0 处
（唯一的 = None 出现在 tests/integration/test_f4_concurrency_clone.py:44）

配合 canvas_widget.py:195 的设计说明——"主线程原地修改 self.design 的标量， 并共享只读的 _cached_outer_image"——可以推导出完整的故障链：

  1. Worker 用素材 A 构建 design，写入缓存图 A
  2. 用户换素材 B，主线程只改 design.pool_outer_material_image = B（标量）
  3. 触发渲染 → image_ops.py:575 取到缓存的图 A
  4. 渲染出旧素材 A → 用户看到"素材残留"

这解释了为什么该 bug 被修了 5 次以上仍会复发：历次修复都在清理症状 （清 mask、清边框、清中间图），而没有触及缓存永不失效这个源头。

修复建议（低风险，约 10 行）：给缓存加上来源校验，让它在素材变化时自动失效。

# core/geometry.py —— 缓存改为 (路径, 图像) 二元组
class CropDesign:
    _cached_outer_image: Image.Image | None = None
    _cached_outer_src: str | None = None   # 新增：记录缓存来源路径

# core/image_ops.py:575 —— 取值时校验来源
cached_img = getattr(design, '_cached_outer_image', None)
if cached_img is not None:
    src = getattr(design, '_cached_outer_src', None)
    if src != design.pool_outer_material_image:
        cached_img = None   # 素材已更换 → 缓存作废，回退到从磁盘加载
改动量 约 10 行 风险 低（缓存失效即自动回退磁盘加载，行为等价） 收益 根治反复复发的素材残留

sketch_parser.py:49-53 五行导入实测共 41 个符号，其中 39 个是私有符号 （日志记录为"9 个"，实际远超）：

导出 39 个私有符号意味着子模块边界形同虚设——改动任一子模块的内部实现， 主模块都可能受影响，改动影响半径与拆分前完全一样。日志"伪模块化"的判断成立。

但请不要据此回退拆分。文件变小对导航、code review、并行开发仍有实际价值。 真正需要补的是公共契约：为每个子模块定义 __all__，只导出真正需要跨模块使用的符号， 私有实现（_ 开头）一律不导出。这样拆分才从"物理切开"升级为"逻辑隔离"。
