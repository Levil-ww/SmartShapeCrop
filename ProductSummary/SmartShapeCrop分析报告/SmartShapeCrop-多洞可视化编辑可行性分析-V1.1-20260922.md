## 1. 结论摘要

### 1.1 一句话结论

**当前多洞功能是"可视的"，但用户"不可编辑" —— 缺口不在渲染，在"反向映射"与"交互命中"两条缺失的回路。**

补齐这两条回路即可实现完整的可视化编辑，**建议采用「叠加层 Overlay」方案**：
新增一个纯 GUI 层的透明交互层盖在现有预览画布上，**`core/` 几何算法与渲染链路一字不改**（零风险），
改动集中在 `gui/canvas_widget.py`（新增绘制 + 命中逻辑）与新建 `gui/pool_holes_overlay.py`。

### 1.2 四维判定

| 维度 | 判定 | 依据 |
|---|---|---|
| **技术可行性** | ✅ 高 | 多洞渲染链路已完整（UNION mask + 逐洞边框 + 逐洞素材），坐标数据 `pool_holes_cm` 已含全部几何真值 |
| **数据结构就绪度** | ⚠️ 中 | 数据够用，但**存的是"绝对坐标"而非"用户语义参数"**，是最大障碍 |
| **改动风险** | ✅ 低 | 方案核心是 GUI 叠加层，`core/` 零改动；现有的 `_paint_notch_overlay` 已证明该模式可行 |
| **实现复杂度** | ⚠️ 中偏上 | 主要难在"反向映射"（绝对坐标 → 用户可理解的宽/高/间距/边距） |

### 1.3 关键数字

| 指标 | 数值 | 说明 |
|---|---|---|
| 多洞数据承载文件数 | **10 个 .py** | 跨 `core/` `models/` `gui/` `workers/` `services/` |
| `pool_holes_cm` 引用点 | **~100 处** | 4 个核心文件的读写点 |
| 每洞存储字段 | **8 个** | `x_cm y_cm w_cm h_cm mt_cm mb_cm ml_cm mr_cm`（+4 个素材字段） |
| 现有 UI 控件数 | **约 50 个** | 8 组 × 6 SpinBox + 7 个间距 SpinBox |
| 预计新增代码 | **550–750 行** | 新建 1 文件（~500 行）+ 改造 2 文件 |
| `core/` 改动 | **0 行** | 几何算法完全不动 |

### 1.4 与既有拆分方案的关系

⚠️ **本报告与 `多洞面板拆分可行性分析-V1.0-20260911.html` 是两件不同的事，可并行、不冲突**：

|  | 面板拆分（既有方案） | 可视化编辑（本方案） |
|---|---|---|
| **解决什么** | 多洞 UI 寄生在水池面板内，控件挤在一起 | 用户看不见洞的位置，只能盲调数字 |
| **层次** | GUI 结构重组（搬家） | GUI 交互增强（新增能力） |
| **核心动作** | 50 个 SpinBox 从 A 面板搬到 B 面板 | 在画布上直接拖拽/框选洞 |
| **可叠加** | 拆分后的面板正好是可视化编辑的"精确输入面板"，**两者互补** | 可视化编辑提供"所见即所得"，与数字面板双通道 |

**建议顺序**：先做可视化编辑（收益直接、风险低），再做面板拆分（整理性质、可延后）。

## 2. 现状：多洞功能的数据链路

### 2.1 完整链路全景

```
① 草图上传 ──► ② 草图解析 ──► ③ design.pool_holes_cm ──► ④ 渲染 ──► ⑤ 预览显示
   (用户拖入)      (多洞识别)       (绝对坐标真值)          (UNION mask)    (只读画面)
                                       ▲                      │
                                       │                      ▼
                                  ⑦ UI 回填 ◄──⑥ 用户盲调 SpinBox
                                  (含手改覆盖)
```

**关键断点**：
- **④ → ⑤ 之间没有回程**：渲染结果只是位图，用户无法从画面上反推/反选某个洞
- **⑤ → ⑥ 之间没有映射**：用户看见画面上的洞，但不知道对应哪个 SpinBox 组
- **⑥ 的输入方式是"盲调"**：改数字 → 点生成 → 看结果 → 再改，**没有即时反馈**

### 2.2 数据真值：`pool_holes_cm` 结构

`core/geometry.py:236` 定义，每个洞是一个 dict（**绝对坐标，画布相对，单位 cm**）：

```python
pool_is_multi_hole: bool = False
pool_holes_cm: list = field(default_factory=list)
pool_holes_gaps_cm: list = field(default_factory=list)   # 仅 UI 展示/调试用
```

实际填充（`workers/property_panel_workers.py:732-739`）：

```python
design.pool_holes_cm.append({
    'x_cm': x_cm,   'y_cm': y_cm,          # 洞左上角绝对坐标
    'w_cm': w_cm,   'h_cm': h_cm,          # 洞宽高（已 +1cm TRIM 扩展）
    'mt_cm': _mt_of(h), 'mb_cm': _mb_of(h),
    'ml_cm': _ml_of(h), 'mr_cm': _mr_of(h),
    # 可选素材字段（由 _on_pool_finished_ok 写入）
    # 'inner_material_path' / '_cached_inner_image' / '_src_design_w_cm' / '_src_design_h_cm'
})
```

> ⚠️ **注意 `w_cm`/`h_cm` 已含 `+TRIM_CM`（1.0cm）扩展**（`workers/property_panel_workers.py:729-730`），
> 这是为补偿"挖洞扩展 1cm / 间距减少 1cm"，保证 `ml + Σ(w+1) + Σ(gap-1) + mr = outer + 1 = canvas`。
> **可视化编辑显示尺寸时必须减去这 1cm**，否则用户会看到比草图大 1cm 的洞。这是最容易踩的坑。

### 2.3 渲染层：已完整支持多洞

**已实现三条独立的多洞渲染分支**（全部是"纯加性保护"，`core/` 无需改动）：

| 功能 | 位置 | 机制 |
|---|---|---|
| **挖洞遮罩** | `core/image_ops.py:1509-1527` | 条件：`mode=='rect_hole'` + `pool_is_multi_hole` + `len>=2`；逐洞 `fill_rect_mask` 后 UNION，**提前 return**，不触碰单洞分支 |
| **逐洞边框** | `core/image_ops.py:1102-1141` | 逐洞独立做 `full_rect & ~shrunk_rect`，得到每洞完整 4 边环，逐洞 OR 合并（否则只剩顶部横条） |
| **逐洞素材填充** | `core/image_ops.py:1562-1596` | 逐洞独立加载 `inner_material_path` 素材并 paste 到对应位置 |

**结论：渲染层不需要任何改动。**

### 2.4 交互层：只有一处「只读叠加」先例

`gui/canvas_widget.py:74-101` 已有 `_notch_overlay` 机制 —— **L 形挖角会在预览图上叠加虚线框 + 角位标签**（`_paint_notch_overlay`，L348-376）。

这是本方案**最重要的可行性依据**：
- 它证明"在已完成渲染的 pixmap 上叠加交互标记"这条路**在本项目已验证可用**
- 它用的是**画布坐标 → 屏幕坐标的换算**（`L367-370`），正是可视化编辑需要的同一套换算
- ⚠️ **但它只画不点** —— 没有 `mousePressEvent`，没有命中测试，**没有反向映射**

**这正是多洞可视化编辑要补的两块拼图。**

### 2.5 参数覆盖链路：已支持「UI 真值优先」

现有链路已支持用户手改数值 → 覆盖草图结果：

```
_detect_multihole_edits()  （gui/property_panel_generate.py:670-725）
    └─ 读取 _mh_active_count / _mh_sp_hole_w/h / _mh_sp_gaps
    └─ 返回 {'active_count','holes_wh','gaps_cm','layout_type'}
        └─ PoolRenderWorker._user_multihole
            └─ 重算 design.pool_holes_cm（workers/property_panel_workers.py:802-899）
```

> ✅ **好消息**：这条链路复用性极高。新增的可视化编辑**不需要新建数据通道**，
> 只需把"拖拽结果"转成同一个 dict 形状喂给 `_user_multihole` 即可。

### 2.6 关键耦合点清单

| # | 位置 | 内容 | 可视化编辑的影响 |
|---|---|---|---|
| 1 | `gui/property_panel.py:96` | `_mh_active_count` 状态真值 | 拖拽增删洞时需同步 |
| 2 | `gui/property_panel.py:702-760` | `_fill_multi_hole_ui()` 回填 | 拖拽后需回填，或反向由它驱动 |
| 3 | `gui/property_panel_layers.py:147-181` | 快照提取（含 `mt/mb/ml/mr` 四元组） | **形状需扩展**（见 §4.4） |
| 4 | `gui/property_panel_generate.py:670-725` | `_detect_multihole_edits()` | **主要接入点** |
| 5 | `workers/property_panel_workers.py:802-899` | UI 真值覆盖 + 坐标重算 | 复用，不改逻辑 |
| 6 | `services/sketch_parser/sketch_parser_multihole.py` | `HoleInfo` / `MultiHoleParseResult` | 不动 |

## 3. 核心问题诊断

### 3.1 问题一：数据是「绝对坐标」，不是「用户语义」

**这是最根本的障碍。**

`pool_holes_cm` 存的是**渲染用的绝对坐标**（`x_cm`/`y_cm`），
而用户思维里想的是**"洞2的宽是 40cm，洞1和洞2间距 5cm"** —— 这是**相对语义参数**。

```
存储层（绝对坐标）          用户语义层（相对参数）
─────────────────          ──────────────────
hole[0]: x=20, w=40   ←→   ml=20, w0=40
hole[1]: x=65, w=45   ←→   gap=5,  w1=45, mr=?
```

**后果**：
- 拖拽 hole[1] 向右 5cm → 改的到底是"洞1的间距"还是"洞2的左边距"？**语义歧义**
- 若 `layout == 'vertical'`，改 `x_cm` 影响的是"左边距"还是"洞宽"？**取决于布局类型**

**解决方向**：新增**反向映射函数** `absolute_to_semantic()`，把绝对坐标还原为用户语义参数。
这需要处理 `horizontal` / `vertical` / `mixed` 三分支（与 `_collect()` 中的正向重算是镜像逻辑）。

### 3.2 问题二：无反向映射 —— 画面上的洞 ↔ UI 控件无法对应

当前 `_paint_notch_overlay` 只对 L 形生效（`canvas_widget.py:77` 有 `mode != 'rect_lshape'` 直接 return）。
多洞模式下**画布上没有任何标记**，用户看着画面上的 3 个洞，无法知道哪个是"洞1"哪个是"洞2"。

**解决方向**：扩展叠加层，为每个洞绘制**编号标签 + 高亮框 + 选中态**。

### 3.3 问题三：无即时反馈 —— 改一个数字要等一次完整渲染

当前流程：改 SpinBox → 点「生成预览」→ `PoolRenderWorker` 完整重跑草图解析与渲染 → 看结果。
**单次往返可能数秒**（大画布 + LOD 渲染 + 全分辨率后台渲染）。

拖动洞的交互若走这条链路，**完全无法用**（拖拽需要 >30fps 的反馈）。

**解决方向**：
- **拖拽期间**：只更新叠加层（纯 QPainter 绘制，亚毫秒级），**不触发渲染**
- **松手后**：触发一次"轻量重渲染"（只重算 mask，不重跑草图解析）
- **选项**：可复用现有 LOD 链路（`canvas_widget.py:243-247`，~400ms）做拖拽后的即时预览

### 3.4 问题四：每洞素材字段的丢失风险 ⚠️

`pool_holes_cm` 重建时会丢失素材字段，代码里已用 `_inherit_material()` 做继承
（`models/design_model.py:345-352`，继承 `'inner_material_path'` / `'_cached_inner_image'` / `'_src_design_w_cm'` / `'_src_design_h_cm'`）。

⚠️ **但 `workers/property_panel_workers.py:850-885` 的 UI 覆盖分支重建 `_new_holes` 时，
只写入 8 个几何字段，未调用 `_inherit_material`** —— 这是**现存的一个既有缺口**：
用户手改多洞参数后生成，每洞素材会丢失，退回纯色填充。

**可视化编辑会高频触发这条路径，因此该缺口必须优先修复（见 §5.4）。**

## 4. 设计方案：可视化 + 手动编辑

### 4.1 总体架构：叠加层（Overlay）方案

```
┌──────────────────────────────────────────────┐
│  PreviewCanvas (QWidget)                     │
│  ┌────────────────────────────────────────┐  │
│  │  paintEvent()                          │  │
│  │  ├─ 渲染结果 pixmap（现有，不动）       │  │
│  │  ├─ _paint_notch_overlay()（L形，不动） │  │
│  │  └─ _paint_pool_holes_overlay() ◄新增  │  │
│  │       ├─ 洞框（实线/虚线）              │  │
│  │       ├─ 洞编号标签 ①②③               │  │
│  │       ├─ 选中态高亮                     │  │
│  │       ├─ 尺寸标注（宽×高）              │  │
│  │       └─ 间距标注                        │  │
│  └────────────────────────────────────────┘  │
│  ┌────────────────────────────────────────┐  │
│  │  mousePress/Move/Release   ◄新增        │  │
│  │  ├─ 命中测试 hit_test_hole()            │  │
│  │  ├─ 拖拽移动 → 更新覆盖坐标             │  │
│  │  └─ 松手 → emit holes_edited 信号       │  │
│  └────────────────────────────────────────┘  │
└──────────────────────────────────────────────┘
          │ pool_holes_edited: list[dict]
          ▼
   PoolHolesOverlayBridge（新建，轻量桥接）
          │ 转成 _user_multihole 形状
          ▼
   既有链路：_detect_multihole_edits() → _user_multihole → 坐标重算
```

**核心原则**：
1. **`core/` 零改动** —— 渲染与几何算法完全不动
2. **复用既有覆盖链路** —— 不新建数据通道，只复用 `_user_multihole`
3. **拖拽期间不渲染** —— 只在叠加层更新，松手才触发渲染
4. **只读优先** —— 叠加层默认只读，需显式进入"编辑模式"才可拖拽（避免误操作）

### 4.2 交互功能清单

| # | 功能 | 交互方式 | 优先级 | 复杂度 |
|---|---|---|---|---|
| F1 | **洞框可视化** | 在画布上为每个洞绘制框 + 编号（①②③…） | **P0** | 低 |
| F2 | **洞选中** | 单击洞框 → 高亮 + 联动右侧 SpinBox 组 | **P0** | 低 |

| F4 | **拖拽改尺寸** | 拖洞框 4 角/4 边手柄 → 改宽高 | **P1** | 中 |
| F5 | **尺寸/间距标注** | 洞框旁显示 `宽×高`；洞间显示间距值 | **P1** | 低 |
| F6 | **缩放/平移画布** | 滚轮缩放 + 中键平移（当前画布无缩放能力） | **P2** | 中 |
| F7 | **增删洞** | 叠加层上右键"在此插入洞" / "删除此洞" | **P2** | 中 |

> **建议首发范围**：F1 + F2 + F3 + F5 —— **已能解决 80% 痛点**（看得见、选得中、拖得动、有标注）。

### 4.3 视觉设计规范

参考现有主题（`IDE Theme: light`），建议配色：

| 元素 | 颜色 | 说明 |
|---|---|---|
| 洞框（未选中） | `QColor(220, 38, 38, 200)` 红色实线 | 与 L 形叠加层同色系，保持视觉一致 |
| 洞框（选中） | `QColor(37, 99, 235, 255)` 蓝色 + 3px 粗 | 明确选中态 |
| 洞编号标签 | 红底白字圆形徽标 | 与 UI 面板中"洞1/洞2"编号严格对应 |
| 尺寸标注 | 深灰文字 + 引线 | 显示 `40.0 × 30.0 cm` |
| 间距标注 | 橙色文字 + 双箭头 | 显示洞间距 |
| 拖拽预览框 | 半透明填充 | 拖拽中的目标位置提示 |

**坐标换算**（复用 `_paint_notch_overlay` 的公式，`canvas_widget.py:367-370`）：

```python
# 画布像素坐标 → 屏幕坐标
px = x + int(round(canvas_x_px * width / canvas_w_px))
py = y + int(round(canvas_y_px * height / canvas_h_px))
# 反向（命中测试用）
canvas_x_px = (mouse_x - x) * canvas_w_px / width
```

✅ **已验证（2026-09-21 源码核实）**：`_paint_notch_overlay` 的换算**本身是正确的** ——
`width`/`height` 是 pixmap 在屏幕上的**实际显示尺寸**（`paintEvent` 传入），
`canvas_w`/`canvas_h` 是全分辨率画布像素（`geometry.py:411-415`）。
两者相除即得"画布像素 → 屏幕像素"的缩放比，**LOD 降采样与窗口缩放都被这个比例自动吸收**，
不会错位。**新叠加层必须复用这同一套公式**（建议抽成 `_canvas_to_screen()` 单一实现，
绘制与命中测试共用，避免两处各写一份而漂移）。

### 4.4 数据流改造：扩展快照形状

**现状**（`gui/property_panel_layers.py:156-178`）：
```python
snap['multihole'] = {
    'active_count': int,
    'holes_w': [float], 'holes_h': [float], 'gaps': [float],
    'mt': [...], 'mb': [...], 'ml': [...], 'mr': [...],
}
```

⚠️ **发现一个既有 bug**：`snap` 中 `mt/mb/ml/mr` 的提取用了 `float(_W[i].value()) and ...` —— 
**当洞宽为 0 时短路返回 `0.0`（falsy），而非 `None`**，导致 Model 层无法区分"用户填 0"与"未填写"。
虽然 Model 层有 `if v and v > 0` 二次防御，**实际影响被掩盖**，但语义上是错的。建议顺手修正。

**改造后**：新增**可选的** `absolute` 字段承载拖拽结果：

```python
snap['multihole'] = {
    # ... 现有字段全部保留（向后兼容）
    'absolute': [                       # ◄ 新增：拖拽后的绝对坐标（优先级最高）
        {'x_cm': float, 'y_cm': float, 'w_cm': float, 'h_cm': float},
        ...
    ] or None,
}
```

`models/design_model.py:apply_ui_snapshot()` 中新增最高优先级的短路分支：
**若 `absolute` 非空 → 直接采用，跳过 layout 重算**（因为拖拽结果本身就是绝对坐标，再重算会破坏用户意图）。

> ✅ **这是纯加性改动** —— `absolute` 为 `None` 时走原逻辑一字不变。

### 4.5 双向同步策略

**核心难点**：拖拽（绝对坐标）与 SpinBox（相对参数）如何保持一致？

**推荐策略：单一真值源 + 单向回填**

| 时机 | 真值源 | 动作 |
|---|---|---|
| 拖拽进行中 | 叠加层临时坐标 | 只更新叠加层绘制，**不回填 SpinBox**（避免抖动） |
| 拖拽松手 | 叠加层坐标 | ① 调 `semantic_from_absolute()` 反算相对参数 ② 回填 SpinBox ③ emit 信号触发渲染 |
| 用户改 SpinBox | SpinBox | 走现有 `_collect()` → 重算绝对坐标 → 刷新叠加层 |
| 生成完成 | `design.pool_holes_cm` | 现有 `_fill_multi_hole_ui()` 回填 → 刷新叠加层 |

**关键**：**任何时刻只有一个真值源**，避免 `_mh_active_count` 被两处共写那类问题的重现。

## 5. 新增优化：多洞模式与自动识别解耦

### 5.1 问题与目标

当前多洞参数区域依赖草图自动识别结果显示。识别成功时可以看到多洞参数，识别失败或识别错误时，用户无法主动进入多洞模式。这会把“识别失败”错误地等同于“功能不可用”，属于交互和状态管理上的缺陷。

优化目标是让自动识别负责提供默认值，让用户选择负责决定最终模式：即使没有识别出多洞，用户也可以手动选择多洞、设置洞数量并编辑每个洞。

### 5.2 状态模型建议

建议把以下状态分开保存：

```text
detected_mode       自动识别出的模式
selected_mode       用户当前选择的模式
detection_confidence 识别置信度或识别状态
holes               当前多洞配置列表
edit_source         auto / manual / mixed
```

处理规则如下：

```text
自动识别结果 → 初始化或推荐界面参数
用户选择结果 → 决定实际生成模式
用户编辑结果 → 作为最终设计数据
```

自动识别失败时仍应显示“单洞 / 多洞”模式选择。用户切换到多洞后，可以通过“添加洞”创建配置；初始洞数量可以默认为 2，也可以显示为空并要求用户设置。自动识别完成后不得静默覆盖用户已经修改的数据，重新识别应提供“应用识别结果”操作。

### 5.3 数据与界面建议

多洞参数应始终使用统一的洞列表承载，列表中的每个洞至少包含位置、宽度、高度、圆角或边距，以及可选的素材字段。模式选择、洞列表和画布叠加层应共享同一份当前设计数据。

界面建议始终保留多洞模式入口。当前选择单洞时，多洞参数可以禁用但不应销毁；切换回多洞时恢复原配置。多洞界面应提供“添加洞、删除洞、复制洞、重新识别、应用识别结果、恢复识别结果”等操作。

### 5.4 校验、保存与兼容

选择多洞后统一执行洞数量、尺寸、边界、重叠、最小间距及工艺限制校验。错误应以具体提示反馈给用户，不能通过隐藏参数规避问题。

旧项目没有多洞字段时按单洞项目加载；新增字段采用默认值；保存和加载均应保留旧数据兼容性。可视化编辑产生的绝对坐标仍可通过现有覆盖链路传递，但需要保留洞素材字段，避免重建 `pool_holes_cm` 时素材退回纯色填充。

### 5.5 推荐实施优先级

第一优先级是模式入口解耦和手动多洞配置，这是本次问题的直接修复；第二优先级是洞框、编号、选中态和参数联动；第三优先级是拖动位置和松手后重渲染；尺寸手柄、增删洞、撤销重做、缩放平移和吸附对齐可在首发版本稳定后再加入。

### 5.6 新增验收场景

- 自动识别成功时，自动填入洞数量和参数；
- 自动识别失败时，仍可手动选择多洞；
- 自动识别为单洞时，用户可以切换到多洞；
- 用户修改后重新识别不会静默覆盖当前设计；
- 多洞参数非法时显示具体原因并阻止生成；
- 保存、加载和旧项目兼容均不丢失多洞数据。

### 5.7 挖洞模式与挖空方式必须分离

水池设计器中存在两个不同维度的设置，不能合并为一个模式开关：

| 设置 | 作用 | 示例 |
|---|---|---|
| **挖洞模式** | 决定洞的数量、位置、尺寸和排列方式 | 单洞 / 多洞 |
| **挖空方式** | 决定洞内最终显示的内容 | 空白（挖去不留白） / 素材填充 |

因此，原有“挖空方式”下拉框必须继续保留在水池设计器主面板中，并与“单洞 / 多洞”并列显示。推荐的面板层级如下：

```text
水池设计器
├── 素材与草图识别
├── 挖洞模式：单洞 / 多洞
├── 挖空方式：空白 / 素材填充
│   └── 素材填充配置
├── 多洞设置
├── 画布预览与可视化编辑
└── 生成预览 / 导出
```

交互规则：

1. “单洞 / 多洞”决定几何参数区域，自动识别只负责提供默认值，不能隐藏多洞入口。
2. “空白 / 素材填充”决定洞内的渲染内容，不应由自动识别结果覆盖。
3. 选择“空白”时隐藏或禁用素材配置，但保留当前素材数据，以便切换回来时恢复。
4. 选择“素材填充”时显示填充素材选择、清除和预览操作。
5. 素材填充必须继续沿用现有匹配逻辑：按花型与目标文件名一致进行素材匹配，并依据每个洞的**当前有效尺寸**进行素材尺寸适配。自动识别尺寸只是初始值，用户修改后的尺寸必须成为后续匹配依据。
6. 用户可以在“多洞 + 空白”和“多洞 + 素材填充”之间自由切换，洞的几何参数不应因此丢失。
7. 可视化编辑层只负责洞的位置、尺寸和编号，不替代或隐藏“挖空方式”控件。

该拆分可以覆盖以下组合：

```text
单洞 + 空白
单洞 + 素材填充
多洞 + 空白
多洞 + 素材填充
```

建议在画布预览中使用不同的视觉提示区分几何边界、空白区域和素材填充区域，避免用户误以为“多洞”本身已经决定了洞内的填充方式。

### 5.8 素材填充逻辑保持不变

现有素材填充逻辑是本次优化的兼容边界，后续实现只能扩展洞的几何编辑能力，不能改变素材选择规则：

- 花型与目标文件名保持一致时，使用对应素材进行填充；
- 每个洞按照当前有效的宽度和高度进行素材匹配、裁剪或缩放；
- 自动识别得到的宽度和高度不具有锁定效果，人工修改后立即以修改值作为新的匹配尺寸；
- 多洞模式下仍按洞逐个处理，不能因为增加了统一的模式选择而把所有洞强制使用同一尺寸或同一素材；
- 用户拖动、修改尺寸或增删洞后，先更新当前洞的几何参数，再按照更新后的尺寸重新执行原有的文件名匹配和尺寸适配流程；
- 找不到匹配素材时，沿用现有的缺失素材处理和提示方式，不静默替换为其他花型；
- 素材路径、缓存图像、源设计尺寸等既有字段必须在重建 `pool_holes_cm` 时正确继承，避免用户编辑后退回纯色填充。

因此，新增功能的职责边界应明确为：

```text
可视化编辑：修改洞的数量、位置、宽度、高度和排列
既有素材逻辑：根据花型、目标文件名和当前有效洞尺寸完成素材匹配与填充
```

这项约束应加入实现评审和回归测试，重点验证“自动识别尺寸为 A 时使用 A 匹配，人工修改为 B 后立即使用 B 重新匹配；每个洞仍使用正确花型素材，且素材尺寸随当前洞尺寸正确变化”。

## 6. 关键技术决策（待拍板）

### 5.1 决策一：叠加层放在哪？（推荐 A）

| 方案 | 做法 | 优点 | 缺点 | 风险 |
|---|---|---|---|---|
| **A. 扩展 `PreviewCanvas`** ⭐ | 在 `canvas_widget.py` 内新增绘制 + 鼠标事件 | 复用现有坐标换算；改动集中一处；无需跨组件通信 | 文件变大（现 377 行 → 约 900 行） | 低 |
| **B. 独立 `PoolHolesOverlay` 组件** | 新建半透明 `QWidget` 盖在画布上 | 职责清晰；可直接复用 `PoolHolesEditPanel` | 需处理两个组件的几何同步、`resizeEvent` 联动 | 中 |
| **C. 换用 `QGraphicsView`** | 重构为场景图架构 | 原生支持拖拽/命中/缩放 | **等于重写画布**，影响所有模式 | **高** |

**推荐 A**：与"改动最小 + 风险最低"的原则一致。若 F6（缩放/平移）确定要做，再考虑迁移到 B。

### 5.2 决策二：语义反算要做完整还是分档？（推荐分档）

`absolute → semantic` 反算需处理三分支，复杂度不低：

| 档位 | 范围 | 说明 |
|---|---|---|
| **最小可用** | 仅 `horizontal` | 覆盖 **90% 业务**（代码注释多处提到"横排占 90% 业务"） |
| **完整** | `horizontal` + `vertical` + `mixed` | 三分支全支持 |

**推荐**：**先做 `horizontal`，其余 layout 拖拽时降级为只读 + 提示**。
理由：`horizontal` 覆盖绝大多数场景，先交付价值；`mixed` 语义本身模糊（代码里就是"退化横排"）。

### 5.3 决策三：洞编号的排序基准

`HoleInfo.index` 注释为"从左到右 / 从上到下"（`sketch_parser_multihole.py:112`），
但 `pool_holes_cm` 是 **list 顺序**，两者需保证一致。

**建议**：以 `pool_holes_cm` 的 **list 顺序**为唯一编号基准（0-based 内部，1-based 显示），
**不按坐标重排** —— 否则用户拖拽改变顺序会导致编号跳变，体验崩溃。

### 5.4 决策四：是否顺手修复素材丢失缺口？（推荐修复）

`workers/property_panel_workers.py:850-885` 重建 `_new_holes` 时未继承素材字段（见 §3.4）。

| 选项 | 影响 |
|---|---|
| **不修** | 可视化编辑高频触发该路径 → 每次拖拽后素材丢失，**用户必然投诉** |
| **修复** ⭐ | 在 `_new_holes.append()` 后补 `update(_inherit_material(i))`（复用 `models/design_model.py:345-352` 的同一模式） |

**推荐修复**，作为可视化编辑的**前置任务**（Phase 0）。
这是"修既有缺陷"，不动新功能，**符合"不改变程序逻辑"的边界**——因为它是修 bug 而非改行为。

### 15.1 问题确认

多洞渲染本身已经按洞读取 `inner_material_path`，但素材匹配入口使用了 `pool_holes_cm` 中的存储尺寸。该字段包含 `CUT_LOSS_CM=1.0cm` 的裁剪扩展，因此实际匹配查询会比用户看到的洞尺寸各大 1cm，导致某些洞匹配到错误尺寸素材或匹配失败。

另外，匹配失败后原有 per-hole 缓存可能继续保留。即使路径已经为空，旧 `_cached_inner_image` 仍可能被渲染分支优先使用，造成洞与素材状态不一致。

当前保留的判断是：原链路已经支持逐洞匹配和逐洞填充，问题排查应继续围绕实际识别参数、目标文件名、模板库文件名及匹配日志进行，不能通过改变尺寸契约来修正显示结果。

## 16. 原有多洞素材匹配逻辑复核（2026-09-23）

根据实际草图和界面截图复核后，确认项目原有逻辑要求保持以下链路：

```text
草图识别洞1尺寸 → 以洞1尺寸匹配洞1素材 → 回填洞1路径
草图识别洞2尺寸 → 以洞2尺寸匹配洞2素材 → 回填洞2路径
```

当前代码中的 `_InnerMatchWorker` 已按 `holes_wh` 列表逐洞构造查询，`_on_inner_match_done()` 也按列表索引逐洞回填 `inner_material_path`；没有将所有洞合并为一个统一尺寸。渲染层随后按每个洞自己的路径和几何区域填充。

为避免改变原有识别逻辑，本次复核不改写匹配尺寸、不额外扣减裁剪扩展，也不改变素材评分规则；仅新增回归测试锁定两个不同洞尺寸必须产生独立查询并回填不同素材路径。

## 17. 导出文件名与多洞独立边距修复（2026-09-23）

### 17.1 导出文件名问题

问题原因：`PropertyPanel.get_output_filename()` 无条件优先读取 L 形面板输出名。水池面板生成后执行导出时，即使最近一次生成来源是水池，也会拿到 L 形面板的文件名。

修复：按 `_last_generate_source` 选择来源：

- `pool`：优先使用水池面板“输出文件名”。
- `lshape`：优先使用 L 形面板“输出文件名”。
- 当前来源控件为空时，继续使用原有回退命名。

这样只修正跨面板文件名串用，不改变 L 形面板自身的文件名逻辑。

### 17.2 多洞单独上边距无效问题

问题原因：多洞参数采集发送给 `PoolRenderWorker` 时只包含每洞宽度、高度和洞间距，没有携带每洞上/下/左/右边距。Worker 重建几何时只能回退到旧识别值，因此用户修改洞1上边距后会被恢复。

修复内容：

- `gui/property_panel_generate.py`：采集 `mt/mb/ml/mr` 四组每洞边距值。
- `workers/property_panel_workers.py`：UI 边距优先于旧识别值，再按原有布局规则重算坐标。
- `tests/gui/test_property_panel.py`：验证修改后的每洞四向边距确实传入 Worker 参数。

几何规则保持不变：横排仍沿 X 方向累加洞宽和间距，竖排仍沿 Y 方向累加洞高和间距；仅替换每洞边距的输入来源。

### 17.3 修改文件

| 文件 | 修改 |
|---|---|
| `gui/property_panel.py` | 按生成来源选择导出文件名 |
| `gui/property_panel_generate.py` | 采集每洞独立边距 |
| `workers/property_panel_workers.py` | 应用 UI 每洞边距 |
| `tests/gui/test_property_panel.py` | 新增文件名和边距回归测试 |
