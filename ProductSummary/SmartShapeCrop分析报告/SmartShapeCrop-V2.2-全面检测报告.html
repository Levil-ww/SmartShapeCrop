4.2 严重问题：17 个测试断言未生效

这些测试函数以 return <bool> 结尾而非 assert，pytest 不校验返回值，因此无论内部计算结果如何，测试都会被标记为通过——形成假通过。受影响的文件恰恰是验证历史 bug 修复的回归测试。

4.3 隐蔽问题：tests/gui/ 是空壳，且在收集期产生副作用

tests/gui/test_gui_sim.py（105 行）名为测试文件，实则是一段脚本式诊断代码：内部没有任何 test_ 函数， 顶层代码在 import 时就会立即执行真实的草图 OCR 解析。README 中记载的「tests/gui/ GUI 模拟测试」实际并不存在。

# tests/gui/test_gui_sim.py 顶层代码（import 即执行） sketch_path = 'scripts/diagnose/_test_sketch1.png' result = parse_sketch(sketch_path, target_outer_w_cm=120.0, target_outer_h_cm=58.0) print("解析结果:")

实测该依赖图片已不存在，导致每次运行 pytest 都会在收集阶段执行一次注定失败的解析并打印诊断输出：

$ pytest tests/gui/ --collect-only -s 测试文件: scripts/diagnose/_test_sketch1.png 目标尺寸: 120.0 x 58.0 cm 解析结果: 成功: False 消息: 文件不存在 ← 依赖图片已丢失 方法: 7step_v7

三重影响：

  • 污染测试环境：每次 pytest 都在收集阶段执行真实 OCR 调用，并 sys.path.insert(0, '.') 污染导入路径
  • 潜在雪崩风险：当前 parse_sketch 对缺失文件返回 False 而非抛异常，所以测试仍跑得通； 一旦未来改为抛异常，收集阶段报错会导致全部 304 个测试无法运行
  • 虚假覆盖信号：目录结构与 README 都表明存在 GUI 测试，实际覆盖率为 0，GUI 层（占代码 19%）目前完全无测试保护
建议：① 立即把该文件移出 tests/（改放 scripts/diagnose/ 并重命名为 _gui_sim_diag.py， 去掉 test_ 前缀即不再被收集）；② 若确有 GUI 测试需求，另起真正的 pytest 用例（可用 QtBot 或 QTest）； ③ 长期看 GUI 层 6,271 行代码零覆盖是明显短板，建议优先为 lshape_panel 等 V2.2 新改动的面板补充测试。
