## 二、L形挖角 Profile Route 两轮迭代（9.8）

### 第一轮：真实素材校准（蔓生花 / 中古雨林）

#### 问题
1. 中古雨林完全没有 L 形边框（切边纯白）
2. 蔓生花沿切边的补画颜色与原素材有色差

#### 根因（真实素材 dump 剖面定位）
- 旧 `_classify_profile`「遇到 field 色段即停」：中古雨林黑描边后是 161px 白边距（= field 色）→ 结构在描边处被截断，只剩 1 层
- `_MAX_LAYERS=4` 装不下 5 层结构；`_LINE_MAX_THICK=18` 小于真实细线（24px）；`_DARK_LINE_MAX_CHANNEL=170` 卡住真实线色漂移（168~179）；field 容差 25 太紧（花田过渡段 L2≈30 漏裁）
- 之前调试用的"蔓生花"jpg 其实是程序输出图（裁剪有图），不是原始素材

#### 修复（`core/lshape_border_route.py` 重写分类算法）
1. **窗口收集**（短边×15%）：巨段深色且色近 field → 限厚收录（克罗棕带直通内部），浅色巨段（花田/白底）丢弃
2. **尾裁 field 段**：容差放宽至 35
3. **定界**：末线后仅保留紧贴的深色平整带（描边+色带结构），其余剔除
4. **分组**：线独立成层，相邻非线段（边距/点带/文字带）无条件合并 —— 层数只由线位置决定，跨边稳定
5. **让位规则**：首层厚黑(≥50) → V13；首层黑细描边+深色第二层（克罗类）→ V13，保护用户已认可的克罗效果

#### 验证
- 蔓生花 PSD (8268×4724) → 5 层 [黑10, 米285(246,232,205), 线25, 点带123, 线25]
- 中古雨林 (5965×3602 等 3 个版式) → 5 层 [黑10, 白162, 线15, 文字带124, 线14]
- 克罗印花 → None 让位 V13（现状不变）
- 端到端渲染：切边米色与素材一致，L 形框线连续转角
- 测试：新增合成雨林全结构夹具，全量 **316 passed + 5 skipped**

### 第二轮：用户反馈三问题修复

#### 问题
1. 蔓生花/中古雨林 L 形只需补到「绿色箭头所指最外内框线」，点带/文字带及其内侧细线不处理
2. 程序实跑蔓生花/中古雨林仍无 L 形边框（离线样张正确）
3. 庄园秘境出现白线 + 黑边带明显变细

#### 端到端诊断结论
- **"无效果"真因**：Profile 实跑确实触发，但 `left` 边最外 2px 出血白边未对齐 → 四边层序错位 → 投票把颜色平均成灰糊，补出来不是素材的黑白框 → 视觉上=无边框
- **庄园秘境剖面**：`[6px 出血白边] → [117px 粗黑带] → [39px 米底]`。117px 粗带不被 `_LINE_MAX_THICK=32` 判为线 → Profile 判废；落到旧路径（且旧路径 `(sx+sy)/2` 在 ROTATE_270 素材下误差 100%+）→ 白线 + 黑带变细

#### 三处修复（`core/lshape_border_route.py` + `core/lshape_border.py`）
1. **锚点对齐**：跳过最外出血边/裁切边，锚点=第一个「近黑+低纹理」段（不限厚度）。`_is_anchor_seg` 用 `_BLACK_MAX_CHANNEL=90`（1px JPEG 灰过渡段 max~116 被排除）。四边层序一致 → 投票颜色真实
2. **层深截断到第二条细线**：描边 + 色带 + 最外内框线 = 3 层封顶。`_MAX_LAYERS 5→3`。line#2 之前的非线段中丢弃花纹段（std≥_FIELD_STD_TOL），只保留紧邻锚点的第一个平整带
3. **庄园秘境粗黑带**：分组时锚点（th>_LINE_MAX_THICK 的粗黑带）独立成层，不被紧随米底平均成灰糊。让位判定函数 `profile_yields_to_v13` 外移到路由层：V13 命中则用 V13，V13 未命中（庄园秘境内侧无主色带→v13=None）则 Profile 接管
4. **几何均值 scale**：`sqrt(sx*sy)` 替代 `(sx+sy)/2`，对 adapt_pool_material 的 ROTATE_270 稳健（旋转后 sx/sy 互换但乘积不变）

#### 验证
- 蔓生花 PSD → `[黑10, 米285(246,232,205), 线25]` 3 层 → 色带颜色与素材一致，止于内框线
- 中古雨林:100x140 → `[黑10, 白147, 线20]` 3 层；:10x100 → `[黑3, 白40, 线4]`
- 庄园秘境:30x115 → `[黑116, 米32]` 2 层；黑带厚度恢复 114px≈素材 118px
- 端到端渲染三素材 L 角局部均正确：白线消除、黑边厚度一致、L 形框线连续转角
- 全量测试 **320 passed + 5 skipped**

#### 关键设计决策
- `_is_anchor_seg`（近黑不限厚）与 `_is_line_seg`（深色+薄≤32）分离：锚点只管"最外起笔"，线只管"细分层"，各司其职
- 让位判定放路由（profile_yields_to_v13）而非 detect 内部返回 None，使 V13 未命中时 Profile 仍能接管
- `_TOTAL_DEPTH_RATIO 0.30→0.50`（粗黑带 60/300 尺寸下 105>90 被误判为图案误检）

## 三、L形挖角渲染 Bug 诊断（9.9）

### 塞纳时光"裁剪有图"L形挖角偏大诊断

#### 问题
用户反馈：双面格-定制-裁剪有图-塞纳时光 66.7x124.8CM，挖角尺寸偏大，向上侵入覆盖绿色椭圆格子下半部。

#### 像素级比对
- 期望挖角区：约 39.9x14.9cm
- 当前挖角区：约 45.8x22.5cm
- 偏差：宽 +5.7cm、高 +7.4cm

#### 根因定位
- 挖角尺寸来自 `core/pool_designer/lshape_sketch_parser.py` 草图 OCR+几何识别
- 几何预检测宽高比 2.43，OCR 结果宽高比 2.04，二者明显偏离
- OCR 把挖角**高度读大了**（22.5 vs 应约18.8cm）
- 疑点：`_resolve_dimensions` 宽高比一致性校验阈值 0.40（40%）过松，未触发几何反推纠正

#### 状态
暂未改码，需用户提供该案草图原图才能复现 OCR 具体误读值并精确定位。

---

### 简织草图诊断：程序无 bug，是期望与草图不一致

#### 诊断结果
- 草图 OCR 6 个数字全读对：A=66.7, B=124.8, C=44.2, D=22.5, E=45.8, F=79
- 几何缺口：cut_w_px=437, cut_h_px=180, outer_w_px=1080, outer_h_px=505
- 自洽度 1.00（完美自洽）
- 程序渲染：45.11 × 23.18 cm（误差 < 1.5%，100% 忠实 OCR）
- 用户期望：39.6 × 14.7 cm，比例 2.701（完全不同比例）

#### 结论
程序对草图是 100% 信 OCR 的，无 bug。用户期望图来自完全不同的输入（可能是手画记忆、另一张草图、或某种业务规则）。

---

### 真实 Bug 定位：渲染挖角边框补全贯穿问题

#### 问题
用户反馈：L形挖角没有保持原本素材的边框，在色带部分加了一个L形黑边，导致挖角没挖干净，左下角还有色带残留。

#### 根因定位
- 真实 bug 在 `core/lshape_border_route.py:441 _fill_layers_vertical_horizontal`
- 当某层 offs[k] >= yc 时，y_lo 回退 0 → 该层从画布顶端一直画到 yc，贯穿整个 L 形垂直切边
- 这就是"L形金/黑边贯穿挖角"的根因

#### 复现条件
- 任意层的累计厚度 ≥ cut_h 时触发
- 当前 simplify 案（cut_h=22.5cm=1329px）+ 3 层总厚 181px 不会触发
- 较小切角（如 8cm 以下）或某些素材（边框 band 较厚）会触发

#### 修复方案（建议，待执行）
1. 把 offs[k] >= yc 时的 y_lo 回退到 0 改掉：超出 cut 高度的层就不画（裁掉多余深度）
2. `_fill_vertical_horizontal`（`lshape_border.py:952`）也类似：水平切边 b[yc:yc+edge, xc:W] 也可能穿越
3. 验证：挖角内不应该有任何边框层（必须等到切边处才上色）

6. **唯一真实循环导入**：`core.image_cropper_mask → core.image_ops → core.lshape_border → core.image_cropper_mask`，当前不崩是因为 image_ops 对 lshape_border 的引用在函数体内推迟执行

### ⚠️ 第四轮：D 档执行 → git gc 事故 → 南烛叫停并撤销

#### 事故经过
1. `git rm --cached -r` 移出 261 个文件索引（工作区文件全部保留）✓
2. 补 `.gitignore` ✓
3. commit 成功，`du -sh .git` 仍为 141 MB
4. **`git gc --prune=now` → 灾难**：`.git` 目录在 gc 过程中被清空，config/HEAD/refs/objects/pack/*.pack/index 全部消失

**结论**：`.git` 目录在 gc 过程中被外部因素清空。推测 Windows 安全软件在 pack 重组时把 `.git` 当威胁隔离/删除，或磁盘/文件系统异常。**不是 git gc 的正常行为。**

#### 教训
1. **`git gc` 在 Windows 上不是零风险操作**，执行前应先做 `.git` 目录级的物理备份（`cp -r .git .git.bak`）
2. **先再读一遍 rc warnings**。3 条 `no corresponding .pack` 是预警，当时没停手
3. 纯索引操作（`--cached`）是安全的；真正动 `.git` filesystem 的命令（gc/repack/fsck --unreachable）才需要前置备份
4. D 档「瘦身」诉求收益有限：只做 `rm --cached` 是止血（未来提交不再含这些文件），历史里的 blob 仍在 pack 中
