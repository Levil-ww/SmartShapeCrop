## 🧱 新增几何形状时先测「模型表达能力」，别先写 UI（2026-09-16 确立）

多边 L 形（9.14）与单边阶梯 L 形（9.16）的分析看起来相似，**性质完全不同**：

- **多边 L 形 = 优先级问题** —— 数据早就算好了，只是被三个收敛点（`argmax`/`or 短路`/`max`）掐成一个角。
  解除收敛即可，估 3–5 天。
- **单边阶梯 L 形 = 模型缺口** —— 现有 `corner` 四值语义（tl/tr/bl/br）在**本质上无法表达台阶**：
  `_get_lshape_cut_rect_at_offset()` 四个分支都强制 cut 贴住两条外廓边，
  而台阶的中间级只贴一条边。这是表达能力不足，不是参数缺失。

**判断方法（可复用的三步只读验证，全部在 `.venv` 下实跑）**
1. **构造目标形状的顶点序列，数凹角（reflex）个数** —— 阶梯实测只有 1 个凹角，
   与单角 L 形相同，**但语义完全不同**（单角 L 形的凹角在 bbox 角附近，阶梯的在对边中段）。
2. **把凹角代入 `_finalize_lshape_geometry` 的 `cut_w_px = maxx - cx` 公式** ——
   阶梯推得 `cut_w = 0` → 被 `build_lshape_mask` 的 `w > 0.5` 过滤丢弃 →
   **静默识别为纯矩形且报 success**。这类"静默失效"是本项目的高频故障模式，必须专门验证。
3. **尝试用现有字段拼出目标形状**（如 `cuts=[('tr',300,60),('br',180,160)]`）——
   看是被校验拦截、还是能通过但几何错误。拦截点会直接告诉你模型缺什么。

**结论**：分析新形状的**第一件事是写只读 POC 验证"模型能不能表达"**，
而不是设计 UI 或估 UI 工期。模型缺口做出来的 UI 是空中楼阁。

### ⚠️ 用真实样例重跑会推翻纯代码推断（2026-09-16 实例）

初版阶梯分析是**纯读代码推断**，得出「识别层也是重灾区，工期 13–20 天」；
拿到真实草图重跑后**两处被推翻**：
1. **识别层其实是好的** —— `n_detected=2`、外框完全正确、OCR 逐角读出 4 个数值与标注逐一吻合。
   缺口只在「凹角列表→形状」的表述方式 → 工期下调到 8–13 天。
2. **真正的根因是 `corner` 标签丢掉了「沿边错位」** —— 阶梯的多个凹角方向判定结果**完全相同**
   （都 `tr`），而多边 L 形靠「不同凹角贴不同角」天然区分。缺的是 `offset_x/y` 而非新算法。

**教训：只要用户能提供真实样例，就用它跑一遍再下结论。** 代码推断容易把「下游表述不足」
误判成「上游识别坏了」，而这两者的工期差 2–3 倍。

### ⚠️ G1 闸口在阶梯场景形同虚设（2026-09-16 新发现，重要）

G1 判据是 `notches_detected != notches_consumed`。严格阶梯实测 `2 == 2` → **天然通过**。
因为「检测到 2 个凹角」是**对的**，错的是「把 2 个凹角组装成形状」这一步。
结果：`success=True` / `g1_blocked=False` / **无任何警告**，但渲染形状与真实阶梯 **IoU 仅 0.9791**
（第二级台阶完全丢失）。

**同类"下游组装"错误 G1 抓不到。** 新增几何模式时需要一层**「形状自洽」校验**：
用产出参数反向拼出轮廓，与识别到的凹角几何比对，不符则降级 success。

**相关约定**：若最终确定要新增几何模式，务必同步检查
`gui/property_panel.py:926`（硬编码索引映射 `{'rect_hole':0,'rect_lshape':1,'ellipse_hole':2}`）
与 `core/app_settings.py:317`（历史源白名单）—— 两处都**静默失效不报错**。
**而"集成进现有面板、不新增 mode/历史源"的方案可同时绕过这两个坑，这是集成的隐性收益。**

## 🎛️ 同面板多形状：不要加「形状类型」，用分组推导（2026-09-16 确立）

多边 L 形与单边阶梯同处 L 形面板，**无需任何「形状模式」选择器**。
判据：**按锚定角（anchor）分组** ——
每组各 1 个 → 多边 L 形；某组 ≥2 个 → 该角是阶梯；两者共存 → 混合（自动支持）。

**三条原则（可复用于任何"同面板多形态"设计）**
1. **不要让用户选形状类型** —— 用户只填尺寸，形状是参数的几何后果。
   让用户先分类 = 转嫁认知负担 + 引入"选错了怎么办"的新问题。
2. **形状是推导结果，不是存储状态** —— 用 `group_by_anchor()` 按需推导，
   **绝不新增 `shape_type` 字段**。存了就要同步，就有"状态与实际不一致"的 bug 面
   （本项目"静默失效"类 bug 的主因之一就是两处各自维护同一语义）。
3. **一个分组函数服务多件事** —— 形状区分 + 约束分层 + 渲染遍历收敛在一处，不易改漏。

**⚠️ 约束必须按分组分层（关键）**：`core/geometry.py:308-324` 的
「同边 cut 尺寸求和 < 边长」对**多边 L 形合理**（各占一段边），
但对**阶梯是语义错误**（同一个角逐级内收，不该求和）。
分层规则：`len(group)==1` 走旧规则；`len(group)>=2` 走阶梯规则（错位单调 + 不重叠 + 最外层不越界）；
**跨角求和时每角只取「最外层级」参与**。

**UI 形态**：平级行 → **父行（选角位）+ 可折叠子行（同角追加级，角位锁定继承）**。
用户靠"填几行、点几次追加"表达形状，界面靠"有没有缩进"呈现形状。

## 几何验证的零改动 POC 套路（2026-09-15 验证有效）

新形状可行性验证不需改源码：写 `scripts/diagnose/_diag_*.py`，只读调用 `core.geometry` 公开原语
（`build_lshape_mask(cuts=...)` / `fill_rect_mask` / `CropDesign` 的 `*_px()`），
用**集合代数恒等式**（而非面积数值）做断言，避免被 PIL 1px 栅格化误差干扰。
实例：`_diag_composite_shape_poc.py`（综合形状 = L形 − 洞），4 项断言全 PASS。
注意 PIL `ImageDraw.rectangle` 边界是**包含式**，面积会偏大约 0.03%，属正常。

**10px 黑框的绘制规则**：当两个移除区域**不相交且不相邻**时，必须**分形状各自绘制环带后 OR 合并**，
不能用"整体 union 再内缩"（联合内缩会在边界产生错误缺口）。判断方法：`m_a & m_b` 为 0 且
1px 膨胀后仍为 0 → 可 OR 合并。
