   ```python
   nodes = [n.identifier for n in g.nodes()]
   ```
   建图约 50s，远快于完整打包，适合发布前漏收自检。
   注：`Analysis()` 直接调用会报 `KeyError: 'workpath'` / `'spec'`，需逐项补齐 `CONF`，
   用 `initialize_modgraph` 更省事。modulegraph 没有 `incoming_edges()`，用 `incidence_edges()`。

5. **`from __future__ import annotations` 是未使用导入扫描的头号假阳性**：

## 三、⚠️ 重大教训：reset --hard 误删 224 个文件及补救

### 现象
`git reset --hard 726d649` 后，`git status` 显示 **224 个文件处于 ` D`（磁盘已删）**，
`.workbuddy/` 目录只剩下 `wheels_backup`：

- `.workbuddy/diag/`、`*.py.bak` 备份、`tmp_samples/`
- `ProductSummary/2026-08/` 等文档

**反常之处**：`git ls-tree 726d649 -- .workbuddy/` 明明包含这些文件，
即目标 commit 里它们都在，reset 过来却变成已删除 —— 属于异常的删除行为。

### 补救（一次成功）
```bash
git checkout -- .        # 从 index 写回工作区
```
执行后 `git status --porcelain | wc -l` → **0**，224 个文件全部回来。

### 为什么能救回来
这些文件都在 git 里被跟踪，所以 index 有完整内容，checkout 能写回。
**而今天上午写的 `.workbuddy/memory/2026-09-09.md` 从未 git add 过，因此永久丢失**，
只能重写 —— 这就是本文件是「第二次写入」的原因。

### 沉淀的规则
1. **reset --hard 之前，bundle 快照是底线**（这次 bundle 就是保险，虽然最终没用到）
2. **reset --hard 之后必须立刻 `git status --porcelain | wc -l` 检查**，
   出现成批 ` D` 就马上 `git checkout -- .` 补救，别慌
3. **`.workbuddy/` 未被 git 跟踪的新文件会在 reset 中丢失** ——
   重要产物（日志、备份）要么及时提交，要么另有离线副本
4. 系统级要求：`.workbuddy` 是项目数据目录，**不是临时缓存，不可删**
