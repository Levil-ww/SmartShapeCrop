### ⭐ 关键经验：日期子目录「提平 vs 下沉」的判断

**偏离了 V1.1 原规划（下沉），改执行提平。** 判断依据值得记住：

触发事实 —— 圆角裁剪工具根目录 16 个 md、**每天只有 1 个**，下沉会造出 16 个单文件碎片目录；
而子目录里的 md **本身已带完整日期前缀**（`20260905-7个回归诊断…md`），提平零信息损失。

决策规则：
1. **文件名已含 YYYYMMDD- 前缀 → 可以提平**，排序天然按时间，可查性不降反升
2. **每天仅 1 个文档 → 绝不建日期子目录**（碎片化）；每天多份kekh才值得下沉
3. **先查 README 有没有记载约定** —— 本项目 README 第 776-778 行已写明
   「圆角裁剪工具按日期命名 / L形挖角按阶段演进 / 水池设计器按日期子目录」。
   提平是**恢复**既有约定，不是发明新规则。**这一步检查能省掉大量主观判断。**

**子目录里的 README 是高质量日度索引，不能删** —— 改名 `<日期>-文档索引.md` 保留全部内容。

3. commit `136c6c7` 成功，`du -sh .git` 仍为 141 MB
4. **`git gc --prune=now` → 灾难**

`git gc` 前 pack 的正常性已由 `git count-objects` 确认（size-pack 84.40 MiB，4 个 pack）。
**但 gc 执行后 `.git` 只剩两个近乎 0 字节的文件**：
`.git/info/refs`(0B) 与 `.git/objects/info/packs`(1B)。
config、HEAD、refs/、objects/pack/*.pack、index **全部消失**。

报错：`fatal: not a git repository`，且 stderr 先出现 3 条
`warning: no corresponding .pack: .../pack-*.idx`。

**结论：`.git` 目录在 gc 过程中被外部因素清空。**
推测 Windows 安全软件在 pack 重组时把 `.git` 当威胁隔离/删除（该机是管理员账户，国产杀软常见行为），
或磁盘/文件系统异常。**不是 git gc 的正常行为 —— 正常 gc 绝不删 config/HEAD/index。**

### 教训（重要）

1. **`git gc` 在 Windows 上不是零风险操作**，尤其配 `--prune=now --aggressive`。
   执行前应先做 `.git` 目录级的物理备份（`cp -r .git .git.bak`），成本几秒到几分钟。
2. **先再读一遍 rc warnings**。那 3 条 `no corresponding .pack` 是预警，当时没停手。
3. 纯索引操作（`--cached`）是安全的；真正动 `.git`  filesystem 的命令（gc/repack/fsck --unreachable）
   才需要前置备份。
4. D 档这种「瘦身」诉求，收益本来有限：只做 `rm --cached` 是**止血**（未来提交不再含这些文件），
   历史里的 blob 仍在 pack 中，要真缩小得重写历史。**为有限收益冒 gc 风险不划算。**
