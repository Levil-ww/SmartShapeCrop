# 2026-09-16 工作日志

## 诊断：L 形挖角「第二轮生成后 GUI 预览空白」（只读排查，源码零改动）

**现象**：第一张草图 L 形解析成功后，清除旧草图、写入新草图再生成，
界面提示「预览已生成」，但 GUI 画布上没有素材（空白）。
截图日志关键点：`_on_pool_finished_ok 被调用: sketch_result.success=N/A`（L 形路径下 sketch_result 恒为 None）。

### 根因（已用脚本实测复现，2 个独立触发路径）

**主因 —— `_apply_quiet → _collect → DesignModel.apply_ui_snapshot` 用 LShapePanel 的
SpinBox 快照反向覆盖了 Worker 刚构建好的 design。**

数据流：
```
PoolRenderWorker 产出 design（正确参数）
  → _on_pool_finished_ok 写回 self.design + 回填 LShapePanel
  → _pool_finish_tail → _apply_quiet()
  → _collect() → _collect_ui_snapshot()  ← 从 LShapePanel 读 corner/cut_w/cut_h/cuts_cm
  → DesignModel.apply_ui_snapshot()     ← 用快照覆盖 design（design_model.py:122-138）
  → render_design(design)  ← 若快照为空则 design 被污染成非法值
```

**触发路径 A：`l_cuts_cm` 被清空 + `l_cut_w/h_cm = 0`**
`clear_lshape_params()`（lshape_panel.py:868）把 `_lshape_params=None`、
外框 SpinBox 重置为 `5.0`；`_collect_ui_snapshot` 的 `lshape` 分支在
`_lshape_panel is not None` 时**始终**构造 dict（不判 `_lshape_params` 是否为 None），
`get_cuts_cm()` 因「未勾选/尺寸为 0」返回 `[]`，`get_cut_w_cm()` 返回 `0.0`。
→ `apply_ui_snapshot` 写入 `d.l_cut_w_cm=0.0`、`d.l_cuts_cm=[]`
→ `render_design` 第 560 行首句 `design.validate()` 抛
`ValueError: l_cut_w_cm 必须为正数，当前值: 0.0`（geometry.py:280）

**触发路径 B：画布尺寸退化到 SpinBox 下限 5.0**
`_sp_w/_sp_h` 范围是 `(5, 500)`（property_panel.py:125）。
`_on_pool_finished_ok` 从 LShapePanel 反推画布：
`self.design.canvas_w_cm = _lp['outer_w_cm'] + 1.0`（property_panel_generate.py:222-227）。
若 `_lp` 为空/外框为 0 → 画布被写成 5.0，
→ `validate()` 抛 `L 形挖角在上边上的尺寸和 30cm 必须小于外边长度 5cm 减 2cm 余量`

**为什么提示「预览已生成」却说空白**：
`_pool_finish_tail`（property_panel_generate.py:488-496）的 `_apply_quiet()` 只 catch
`ValueError`，且 `format_design_validation_error` 的分支只匹配 `"L 形挖角在...上的尺寸和"`；
**路径 A 的报错文案是「l_cut_w_cm 必须为正数」，不命中该分支**，
`_set_pool_status` 的文案被覆盖成通用「参数校验失败」，用户不容易把它和「预览空白」联系起来。
而 `logger.info("[PropertyPanel] 预览已生成")` 在 `_apply_quiet()` **之后**——
异常路径下 `return` 会跳过它；截图里出现「预览已生成」说明走的是
**另一条分支：异常被 `_on_pool_finished_ok` 外层 except 吞掉**，
落到 `_set_pool_status(f"✅ 生成完成（部分失败：{e}）")` + `_apply_quiet()`（:370-376）。

**结论（一句话）**：
L 形第二轮生成时，LShapePanel 的参数快照为空（清除草图把它清了，
但 `_collect_ui_snapshot` 仍无条件从 Panel 取值并覆盖 Worker 的 design），
导致 design 被写成非法值 → `validate()` 抛错 → 渲染中断 → 画布空白。

### 修复方向（尚未实施，待南烛确认）

1. **`_collect_ui_snapshot` 的 lshape 分支加守卫**：
   `_lshape_params` 为 None 时传 `None`（让 Model 走默认分支），
   而不是构造一个「全 0」的假快照 —— 这是最小、最对症的改动。
2. **`_on_pool_finished_ok` 的 L 形覆盖加有效性校验**：
   `_lp.get('outer_w_cm', 0) > 0` 已有判断（:224/:226），
   但**未校验 `cuts_cm` 非空 / `cut_w_cm > 0`**，需补齐。
3. **`format_design_validation_error` 补分支**：
   让「l_cut_w_cm 必须为正数」也给出面向用户的提示，
   避免报错被压缩成无信息的「参数校验失败」。

### 关键事实（后续排查复用）

- **`render_design` 第一句就是 `design.validate()`**（core/image_ops.py:560），
  任何非法 design 都会在渲染入口直接抛错，不会产出空白图 ——
  「提示成功 + 画布空白」几乎一定是异常被上层吞掉，而不是渲染出了白图。
- **L 形路径下 `sketch_result` 恒为 `None`**（PoolRenderWorker 第 423-424 行：
  `is_lshape=True` 时 `sketch_result=None`），因此日志里的
  `sketch_result.success=N/A` 是**正常的**，不是故障信号。
- **`_collect_ui_snapshot` 无条件信任 LShapePanel 状态**，
  这是「Worker 的正确值被 UI 的空值覆盖」这一类 bug 的通用发源地。
- 实测：本项目 `.venv` 跑诊断脚本正常（`F:\SmartShapeCrop\.venv\Scripts\python.exe`）。
  Bash 工具下 `rm` 已被 shim 拦截失效，删除文件请用 Python 的 `os.remove`。

#### 修正 ①：识别层其实是好的（V1.0 判断过悲观）

实测 `parse_lshape_sketch()` 输出：
```
success=True / notches_detected=2 / notches_consumed=2 / g1_blocked=False
outer_w_cm=93.5 ✓  outer_h_cm=55.0 ✓   (外框完全正确)
```

**结论**：识别层已能检测 2 个凹角、能逐角 OCR、外框准确。
**缺口不在识别，而在「凹角列表 → 形状」的表述方式** → 识别层改造从「高风险 4–6 天」下调为
「换公式 1–2 天」，**总工期 13–20 天 → 8–13 天**。

#### 修正 ②：真正的根因是 `corner` 标签丢掉了「沿边错位」

两个凹角的方向判定结果**完全相同**：
```python
凹角1 (950,137): h_nbr=(167,0)→sx=+1, v_nbr=(-1,-91)→sy=-1 → corner='tr'
凹角2 (1118,194): h_nbr=(142,0)→sx=+1, v_nbr=(-1,-57)→sy=-1 → corner='tr'
```
`corner ∈ {tl,tr,bl,br}` 只回答「朝向哪个 bbox 角」，**不回答「是该角的第几级、沿边错位多少」**。
多边 L 形靠「不同凹角贴不同角」天然区分；阶梯的凹角**全贴同一个角**（都 tr），只能靠错位量区分。

#### 修正 ③（最重要的新发现）：当前会【静默出错】

把识别结果送进几何层渲染，与真实阶梯做像素级比对：
- 真实保留面积 609,888 px / 现有渲染 622,888 px / **差异 +13,000 px**
- **IoU = 0.9791**（第二级台阶完全丢失；y=20/60/100 三行最右像素均不符）

⚠️ **但 `success=True`、`g1_blocked=False`、无任何警告** ——
**G1 闸口（`notches_detected != notches_consumed`）在阶梯场景下形同虚设**：
`2 == 2` 天然通过，因为「检测到 2 个凹角」是**对的**，错的是「把 2 个凹角组装成形状」这一步。
**需要一层新的「形状自洽」校验**（CutRect 拼出的轮廓面积 ≠ 凹角推得面积 → 降级 success）。

#### 仍成立的 V1.0 结论（模型缺口）

| # | 位置 | 实测证据 |
|---|---|---|
| ① | `core/geometry.py:291` | `l_cuts_cm 不允许重复角位: 'tr'` —— 同角位两级台阶直接抛异常 |
| ② | `core/geometry.py:707-714` | `_get_lshape_cut_rect_at_offset` 四分支**强制 cut 贴两条外廓边**，台阶中间级只贴一条 → 无一分支能表达 |
| ② | `core/geometry.py:308-324` | 用 `tr+br` 拼同边阶梯被拦：`尺寸和 28cm 必须小于外边长度 24cm` —— 对**同边阶梯是语义错误**，必须重写 |
| ③ | `lshape_sketch_parser.py` | `cut_w_px = maxx - cx` 公式在阶梯下**系统性算错**（实测凹角1 推得 `cut_w=310px`，真实级1 仅 `10cm=125px`）→ 必须改走「相邻顶点差值」 |

### 推荐方案：`CutRect` 列表化（带「锚定角 + 沿边错位」）

```python
@dataclass
class CutRect:
    anchor: Literal['tl','tr','bl','br']  # 锚定哪个 bbox 角（决定贴哪两条外廓边）
    offset_x_cm: float   # 从锚定角起算的水平错位量
    offset_y_cm: float   # 从锚定角起算的垂直错位量
    w_cm: float
    h_cm: float
```

**关键性质：旧模型是新模型的严格子集**（旧字段 offset 恒 0），兼容层可做到零行为变化：
- 旧单角 L 形（tr 30×8）= `CutRect('tr',0,0,30,8)`
- 旧多边 L 形（tr+bl）= 两个 offset 全 0 的 CutRect
- **本例阶梯** = `[CutRect('tr',0,0,10,6.5), CutRect('tr',10,6.5,8.5,3.5)]`

**识别层改造极小**：`concave` 坐标**一直在 `all_corners` 里**，只是下游没用它算错位量。
只需 `anchor = corner`（已有）、`offset = |conc - anchor_bbox角|` —— **「换公式」而非「新算法」**。

四期路线图（修订）：`CutRect`模型+渲染(2–3d) → 识别层补 offset(1–2d) → GUI 同角位子行(2–3d) → 边框补全(3–5d)，**合计 8–13 天**。

### 两条重要判断

- **边框补全是唯一硬骨头**（与 9.14 多边 L 形结论一致）。台阶带来**非 bbox 角的凹角**，
  `lshape_border.py` 现有 6 个函数被 `cut_corner` 字符串贯穿。`cuts` 入参已是列表，主要缺在凹角几何。
- **建议与 F-1（多 L 形 + 中间洞复合）合并规划** —— 同一套 `CutRect` 模型的自然延伸，
  现在把模型设计到位，F-1 只需扩 UI 和识别，避免二次重构。

## 追问：都集成在 L 形面板，两种形状怎么区分？

**产物**：`ProductSummary/L形挖角设计器/20260916-单边阶梯与多边L形在同一面板的区分设计.md`

### 核心结论：不需要区分 —— 因为形状是参数的必然结果，不是用户的选项

**判据只有一条：按锚定角（`anchor`）分组**

| 情形 | anchor 分组 | 语义 |
|---|---|---|
| 每组各 1 个 | `tr×1, bl×1` | 多边 L 形 |
| 某组 ≥2 个 | `tr×2` | 单边阶梯 |
| 混合 | `tr×2, bl×1` | 阶梯 + 多角（自动支持） |

实测验证（`CutRect` 模型下天然成立，无需额外字段）：
```
单角L形          anchor 分组: tr×1
多边L形          anchor 分组: tr×1  bl×1
本例阶梯         anchor 分组: tr×2(阶梯)
混合(阶梯+多角)   anchor 分组: tr×2(阶梯)  bl×1
```

### 三条设计原则

1. **不要让用户选形状类型。** 用户脑子里只有尺寸（「先退 10、下沉 6.5，再退 8.5、下沉 3.5」），
   没有形状分类。让他填尺寸，形状自己浮出来。让用户先分类 = 把系统认知负担转嫁给用户，
   且引入「选错了怎么办」的新问题。

2. **形状是推导结果，不是存储状态。** 用 `group_by_anchor()` 按需推导，
   **不要新增 `shape_type` 字段** —— 存了就要同步，就有「状态与实际不一致」的 bug 面。
   （本项目「静默失效」类 bug 的一大来源正是两个地方各自维护同一语义。）

3. **一个分组函数服务三件事**：形状区分、**约束分层**、渲染遍历。收敛在一处就不易改漏。

### ⚠️ 附带解决的关键问题：几何约束必须分层（原方案没讲透）

`core/geometry.py:308-324` 现有约束是**「同一条边上所有 cut 的边尺寸之和 < 边长」**：

- **对多边 L 形** `tr(28)+bl(30)` → 两个角各占一段边，求和**合理** ✅
- **对阶梯** `tr(10)+tr(8.5)` → 同一个角逐级内收，**求和是语义错误** ❌
  （实测：用 `tr+br` 拼同边阶梯被拦 `尺寸和 28cm 必须小于外边长度 24cm`）

**分层后的规则**：
- `len(group)==1` → 沿用旧规则（该 cut 不越界）
- `len(group)>=2` → 阶梯规则（各级错位单调 + 不重叠 + 最外层不越界）
- **跨角求和时每角只取「最外层级」参与**（阶梯总占用 = 最外层级尺寸）

### UI 方案：4 个平级行 → 父行 + 可折叠子行

现状（角位互不关联）→ 改为：
```
☑ 右上角   宽[10.0] 高[6.5]              ← 父行
   └ ☑ 第2级  宽[8.5] 高[3.5]  [+ 追加一级]  ← 子行，角位锁定继承父行
☐ 左下角   宽[ 0.0] 高[0.0]
```
用户靠「填几行、点几次追加」表达形状，界面靠「有没有缩进」呈现形状。
建议另加**只读**的「形状预览」标签（如「右上角 2 级阶梯 · 外框 93.5×55.0 cm」）
作 G3 人工核对辅助 —— **只读、不参与设计、不要求选择**。

### 待确认（阻塞 UI 设计）

1. **是否需要「逐级外扩」**（第二级比第一级大）？
   只需内收 → `offset` 可自动推导 = 上级尺寸，子行 **2 个输入框**；
   需外扩 → `offset` 必须显式填写，子行 **4 个输入框**。
2. **最多几级**（本例 2 级）？2 级 → 最简单；3–4 级 → 需支持继续追加；不限 → 需滚动区。
3. **子行角位是否锁定继承父行**？（建议锁定，避免「子行既是父角又是别的角」的歧义）
